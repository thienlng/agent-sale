## 0. Current state (2026-11-08)

Production is one VPS (`/opt/apps/rapiz`, Docker Compose, `infra/deploy/compose.yml`).

| Asset | Today | Gap |
|---|---|---|
| PostgreSQL (`pgdata` volume) | `backup.sh`: `pg_dump -Fc` daily at 03:15 UTC into `backups/` on the same disk, 14 days | Same disk as the data: losing the server loses the backups. RPO up to 24 h. No point-in-time recovery. |
| Object storage (SeaweedFS, `s3data` volume, bucket `rapiz`) | nothing | Losing the volume loses every product, lodging and chat picture. |
| `.env` (`SECRETS_ENCRYPTION_KEY`, JWT keys, VAPID pair, S3 keys, Meta secrets) | nothing | Without `SECRETS_ENCRYPTION_KEY` a restored database cannot decrypt channel tokens; a new VAPID pair invalidates every registered device. |
| Restore tests | never run | An untested backup is not a backup. |
| Workspace export | per-screen Excel/CSV for orders, FAQs, products only | No whole-workspace export (`SET-10`). |

## Phase 1 — platform backup and disaster recovery

### 1.1 Targets

- **RPO ≤ 1 minute** for PostgreSQL (better than the 15-minute NFR), point-in-time recovery to any second of the last **30 days**.
- **RPO ≤ 24 hours** for object storage and server config.
- **RTO**: measured by the weekly drill (§1.6), target ≤ 4 hours for a full server loss.
- Off-site copy on a **vendor-neutral S3-compatible destination** (Cloudflare R2, Backblaze B2, MinIO/SeaweedFS on another host…). The owner has not chosen a provider; nothing in the design depends on one.
- Everything is **encrypted before it leaves the server**; the destination never sees plaintext.

### 1.2 What is backed up

| Data | Tool | When | Retention |
|---|---|---|---|
| PostgreSQL WAL | WAL-G `wal-push` from `archive_command` (libsodium encryption, zstd compression) | continuously; `archive_timeout = 60` forces a segment at least every minute | as long as a retained base backup needs it |
| PostgreSQL base backup | WAL-G `backup-push` | nightly 19:00 UTC (02:00 Vietnam) | 30 full backups (`delete retain FULL 30`) → PITR over 30 days |
| Object storage bucket `rapiz` | `rclone sync` from SeaweedFS S3 to an rclone `crypt` remote; overwritten or deleted objects moved with `--backup-dir` to `media:deleted/<UTC date>/` (same crypt remote) | nightly, after the base backup | live mirror + deleted/overwritten objects for 30 days |
| `.env`, `compose.yml` | `tar` → `age` encryption → rclone copy to `config/<UTC timestamp>.tar.age` | nightly | 30 copies |
| Local `pg_dump` (existing `backup.sh`) | kept for fast on-host restores and the pre-deploy backups in the runbook | daily + before deploys | **7 days** (down from 14; off-site copies replace the long tail) |

**Not backed up, on purpose:** Redis (BullMQ queues and caches; a lost queue is rebuilt by the outbox/reconcile jobs, and inbound webhooks are idempotent), the `hermes` volume (test-only ChatGPT login; production uses the OpenAI API), Caddy volumes (certificates are re-issued).

### 1.3 Configuration (`.env`)

```
BACKUP_S3_ENDPOINT=          # e.g. https://<account>.r2.cloudflarestorage.com
BACKUP_S3_REGION=auto
BACKUP_S3_BUCKET=
BACKUP_S3_ACCESS_KEY=
BACKUP_S3_SECRET_KEY=
BACKUP_WALG_KEY=             # libsodium key (base64, 32 bytes), generated by bootstrap.sh
BACKUP_RCLONE_PASSWORD=      # rclone crypt password (obscured at use), generated by bootstrap.sh
BACKUP_RCLONE_SALT=          # rclone crypt password2, generated by bootstrap.sh
BACKUP_AGE_RECIPIENT=        # age public key; the private key is NOT stored on the server
BACKUP_ALERT_EMAIL=          # who gets backup alerts (sent with the existing RESEND_API_KEY)
```

Layout in the bucket: `wal-g/` (WAL-G prefix), `media/` (rclone crypt; `current/` and `deleted/<date>/`, names encrypted), `config/`, `drills/` (drill reports, plaintext, no data).

**Unconfigured is a supported state.** If `BACKUP_S3_BUCKET` is empty: `archive_mode` is still `on` but the archive command (`wal-g-archive`) reports success without uploading, so WAL is recycled as before; the nightly script and drill print `backup: off-site not configured` and exit 0, and the check script sends one "backups not configured" alert per day if `BACKUP_ALERT_EMAIL` is set. Existing deploys keep working unchanged.

### 1.4 Break-glass kit

Three secrets are needed to restore and must live **outside the server** (owner's password manager): `BACKUP_WALG_KEY`, `BACKUP_RCLONE_PASSWORD` + `BACKUP_RCLONE_SALT`, the **age private key**, plus the S3 credentials. `backup-keys.sh` generates the keys, writes the public/derived values to `.env`, prints the kit **once**, and stores nothing else. The age private key is never written to the server: a compromised server cannot read old config backups, and `.env` still holds the WAL-G and rclone keys the server needs to write backups.

### 1.5 Components (all in `infra/deploy/`)

1. **`postgres/Dockerfile`** — `FROM pgvector/pgvector:pg16`, adds WAL-G, rclone (pinned releases, SHA-256 verified), age and the scripts `wal-g-archive`, `pg-drill-entrypoint`, `rapiz-backup`. Compose builds it on the server as `rapiz-postgres:local` (`deploy.sh` runs `compose build postgres`; CI builds only the app and edge images). Postgres runs with `archive_mode=on`, `archive_command='/usr/local/bin/wal-g-archive %p'`, `archive_timeout=60` and joins the `default` network for egress to the bucket. The first deploy restarts Postgres once (~10 s). Tools containers on the same image: `backup` (rclone/age jobs) and `pgdrill` (restore target).
2. **`backup-nightly.sh`** (cron 19:00 UTC) — WAL-G `backup-push` inside the postgres container, `delete retain FULL 30 --confirm`; rclone media sync (`--backup-dir`), prune `media-deleted/` older than 30 days; config tarball → age → rclone; prune `config/` to 30. Each step runs even if an earlier one failed; the script exits non-zero if any failed and records the last success/failure time of each step in `backups/backup-status` for the check.
3. **`backup-check.sh`** (cron every 5 min) — alerts by email (Resend HTTP API, `curl`) when: `pg_stat_archiver.last_archived_time` older than 15 min or `last_failed_time` newer than `last_archived_time`; newest WAL-G base backup older than 26 h; last nightly step failed; last drill failed or older than 8 days; disk usage of the Docker data root > 85 % or `pg_wal` > 5 GB. One email per alert key per hour (state in `backups/.alerts/`). This is the guard for the main WAL-archiving risk: if the destination is down, Postgres keeps WAL on disk until it fills.
4. **`restore-drill.sh`** (cron Sunday 21:00 UTC) — starts a throwaway container from the same postgres image on an isolated network with a temporary volume, `wal-g backup-fetch LATEST`, recovers to the end of the archived WAL, starts it, and checks: row counts of `workspaces`, `conversations`, `conversation_messages`, `orders`, `contacts` are > 0 and within 1 % of production; the newest `conversation_messages.created_at` is within 15 minutes of production's. Then fetches and decrypts 20 random media objects and compares their SHA-256 with the source, and confirms the newest config archive exists (it cannot decrypt it — no private key on the server — so the owner decrypts one during the quarterly manual check in the runbook). Writes the duration (real RTO for the database part) and result to `backups/drills.log` and `drills/<date>.json` off-site; removes the container and volume. Needs free disk ≥ 2 × database size; skips with an alert otherwise.
5. **`backup.sh`** — unchanged except retention 14 → 7 days.
6. **`bootstrap.sh` / `deploy.sh`** — install all backup cron lines idempotently (`install_backup_cron` in `backup-lib.sh`, also on every deploy) and build the postgres image; keys come from `backup-keys.sh`.

### 1.6 Runbook

New `docs/runbooks/backup-and-restore.md`, linked from `deploy-vps.md` (which replaces its "off-site backup is not automated yet" note):

- **A. Undo a mistake** (rows deleted/edited by error): PITR into a side container to a timestamp before the mistake, copy the needed rows back with `psql`/`COPY`; production is not stopped.
- **B. Whole server lost**: new VPS → `bootstrap.sh` → put the break-glass kit into `.env` → `wal-g backup-fetch LATEST` into a fresh `pgdata` → rclone media back into SeaweedFS → decrypt and compare the newest config archive → `deploy.sh`. Each step with commands and expected output.
- **C. Media lost**: rclone from the crypt remote back into the bucket (single object, prefix or all).
- **D. Quarterly manual check**: owner decrypts the newest config archive with the age private key.
- Alert reference: each `backup-check.sh` alert, what it means, what to do.

### 1.7 Testing

- `shellcheck` on every script.
- `infra/deploy/test/backup-e2e.sh` (manual, needs Docker): brings up the postgres image, a source SeaweedFS and a second SeaweedFS as the off-site destination; writes rows, archives, records timestamp T, writes more rows, restores to T in a throwaway container and asserts the rows at T are present and the later ones absent; syncs, deletes and restores a media object; runs `restore-drill.sh` and `backup-check.sh` against the stack (alert sent to a stub). The PR records its output. It is not wired into CI (needs Docker-in-CI; `.github/` changes need the maintainer).

### 1.8 Owner actions to switch it on

1. Create a bucket on the chosen provider (enable Object Lock / versioning if offered) and an access key limited to that bucket.
2. Run `./backup-keys.sh` on the server, store the printed kit in the password manager.
3. Fill `BACKUP_*` in `.env`, `./deploy.sh <sha>`.
4. Run `./backup-nightly.sh` and `./restore-drill.sh` once by hand; both must pass.

## Phase 2 — workspace data export (`SET-10`)

### 2.1 User flow

Settings → new **"Dữ liệu"** section → "Xuất toàn bộ dữ liệu" with a checkbox "Kèm ảnh và tệp" (off by default; can be large). Only members with the new permission `workspace.export` (owner and admin roles) see it. Clicking starts an export; the section lists recent exports with status (`queued`, `running`, `ready`, `failed`, `expired`), size and a download button. When ready the owner gets an in-app notification and an email. Downloads expire after **7 days**; the file is then deleted.

Limits: one running export per workspace, at most 3 per workspace per day.

### 2.2 Archive contents

A ZIP named `rapiz-<workspace slug>-<UTC date>.zip`:

- `README.txt` (Vietnamese): what each file is, every column, timestamps in UTC ISO 8601, money in VND integers.
- One **CSV per entity** (UTF-8 with BOM so Excel shows Vietnamese correctly, RFC 4180 quoting), stable ids kept so files can be joined: `customers.csv` (from `contacts`), `customer_notes.csv`, `conversations.csv`, `messages.csv`, `orders.csv`, `order_items.csv`, `products.csv`, `knowledge_items.csv` (FAQ/training), `lodging_properties.csv`, `lodging_units.csv`, `lodging_bookings.csv`, `requests.csv` (saas/education/spa), `members.csv`, `billing_history.csv`. Entities a workspace has no rows for still get a header-only file.
- `bots.json` — bot configuration (persona, instructions, actions), without secrets.
- `media/` (only when "Kèm ảnh và tệp" is on) — files referenced by the rows above, with the CSVs pointing at their relative paths.

Never exported: channel access tokens, API keys, webhook secrets, password hashes, email codes, other workspaces' data, platform-internal tables (ledger internals beyond the workspace's own billing history, audit internals).

### 2.3 Architecture

- New backend module **`dataexport`**, created with `pnpm gen module dataexport` (tier and allowed imports per `docs/ARCHITECTURE.md`). It owns the `data_exports` table (`id`, `workspace_id`, `requested_by`, `include_media`, `status`, `object_key`, `size_bytes`, `error_code`, `created_at`, `finished_at`, `expires_at`) with RLS on `workspace_id` (ADR-004).
- It **does not read other modules' tables.** Each data-owning module (crm, conversation, commerce, knowledge, lodging, saas, bot, team, billing) exposes an export method on its public `api/` facade (shape shared as a `WorkspaceExportSource` type in `packages/contracts`: file name, column list, async row pages, referenced media keys) and `dataexport` imports only those facades, per `docs/ARCHITECTURE.md`. Each source reads its own tables under the workspace's RLS context in pages/cursors (no full-table loads; performance budget in `docs/16-performance-and-scale.md`).
- The job runs on the **worker** (BullMQ queue `dataexport`), streams rows into a streaming ZIP writer and uploads with S3 multipart to a **separate private bucket `rapiz-exports`** (the `rapiz` bucket allows anonymous read, so exports must never go there). The API streams the download after checking the permission and workspace; no public or presigned URL is handed out.
- Every export request and download writes an audit event (`workspace.data_exported`, `workspace.data_export_downloaded`) as required by `docs/09-security-and-compliance.md`.
- A daily worker job deletes expired objects and marks rows `expired`.
- Logs carry ids, counts, sizes and error codes only — never row content.

### 2.4 Testing

- Per source: tenant-isolation test (rows of workspace B never appear in A's export), column/header test, secrets-exclusion test.
- Job: end-to-end test that builds an export for a seeded workspace, opens the ZIP and checks file list, headers, BOM and row counts; failure path sets `failed` with an error code; expiry job.
- API: permission test (staff without `workspace.export` gets 403), rate-limit test, cross-workspace download denied.
- Web: the "Dữ liệu" section states (empty, running, ready, failed, expired) and the permission gate.

### 2.5 Out of scope

Workspace deletion (rest of `SET-10`), importing an export back, scheduled exports, per-entity export filters, exporting to Google Drive.
