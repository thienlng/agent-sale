# ADR-015: Agent harness v2 — free-text Hermes-style agent loop for the reply agent

- Status: Proposed (decisions taken by the owner on 2026-10-31; accepted when the harness v2 PR merges)
- Date: 2026-10-31
- Decision makers: thienlng (owner)
- Supersedes in part: [ADR-010](ADR-010-isolated-hermes-runtime.md) ("Hermes has no tools", Hermes as a runtime provider) and [ADR-014](ADR-014-tool-calling-for-the-reply-agent.md) (the JSON final reply, the 4-round loop, the 3-images-per-turn cap, emulated tools as the Hermes path)

## Context

After ADR-014 the reply agent called tools, but the harness around it stayed tight: at most 4 tool rounds, tool calls emulated as JSON inside the prompt for the Hermes pipe, one JSON envelope per turn (`{outcome, reply, sources, imageIds ≤ 3}`, the `FinalReply` type) with a format retry and prose salvage, one retry on provider errors, history cut at 20 turns, and a number guardrail that replaced a whole answer with the fallback message when a figure was not found in the sources. Next to Hermes, the agent the owner uses daily, the bot felt rigid: it could not show several products with their own pictures, it promised "để em kiểm tra" instead of looking things up, it forgot early facts in long chats, and a customer writing again mid-turn got an answer to the old message.

The agent core must stay in TypeScript in the same process as tenant data (Node cannot host the Python Hermes loop; a Hermes-side loop would need network tool calls and a second authority over tenant data). So the harness techniques of Hermes are ported, not Hermes itself. Design: `docs/superpowers/specs/2026-10-31-agent-harness-v2-design.md`; implementation ledger: tasks 0–9 of the harness v2 plan.

## Decision

Owner decisions of 2026-10-31:

1. **Free-text output, pure Hermes style.** The model's final answer is plain text, split into Messenger bubbles by `splitReply` and sent as the message with `via: 'final'`. There is no JSON envelope, no `responseFormat` on the reply path and no `FinalReply`/`ModelReply` parsing, format retry or prose salvage. The outcome is derived: `handoff` if the `handoff` tool ran (or the provider refused), `answered` if anything reached the customer, otherwise `fallback` with the bot's own fallback message (never model text).
2. **Optional `send_message` tool.** `send_message({ text?, imageIds? })`: text ≤ 2 000 chars, at most 3 picture ids per message, any number of calls per turn, including mid-loop. Messages go out as they are produced (800 ms apart on Messenger); the playground collects them. Not offered on public comment replies. An empty final answer after at least one `send_message` is fine. The per-turn 3-image cap is gone. `handoff({ reason })` is a tool and ends the turn.
3. **Budget per turn: 10 rounds or 120 s.** `AGENT_MAX_ROUNDS = 10`, `AGENT_BUDGET_MS = 120_000`, a wrap-up notice at 80 % of the budget, per-call timeout `clamp(remaining / 2, 15 s, 60 s)`, then one call with tools forbidden (`tool_loop_limit` if it still calls tools). Tool execution follows Hermes: name and argument repair, read-only tools in parallel (max 8), writes in order, results capped at 12 000 chars, three invalid-only batches stop the turn (`invalid_tools`). Provider calls get error classes, up to 3 jittered retries with `Retry-After`, and the tier's fallback model.
4. **Interrupt, not queue or steer.** A newer customer message (or a takeover, or the bot turned off) interrupts the running turn before the next model call or after a tool batch. Messages already sent stay sent; the turn's tool work (`carry`) is handed to a re-run that answers every customer message of the burst. At most 3 re-runs per burst; the last one runs to completion.
5. **Keep the existing batching, add a NOTIFY wake-up.** The ingress quiet window stays (`EVENT_QUIET_MS` = 700 ms, capped by `EVENT_MAX_WAIT_MS` = 4 s; the old 300 ms poll is now only the fallback cadence). An `AFTER INSERT` trigger on `channel_webhook_events` runs `pg_notify('rapiz_ingress', id)`; the agent process listens on one dedicated connection and ticks at once, with a trailing tick after the quiet window. The interval poll becomes a 5 s safety net (300 ms while the listener is down; reconnect backoff 1 s → 30 s).
6. **No number guardrail on the reply path.** A reply is no longer replaced because a figure is missing from the sources. `domain/grounding.ts` (`ungroundedFigures`) stays in the repository with its tests; the evals use it (`numbers_only_from_sources`). The owner will revisit what counts as a wrong price.
7. **Hermes stays only as the development pipe to ChatGPT.** The bridge (ADR-010) gains contract v2 with native tool calls (`/health` → `nativeTools`); it never executes tools. The emulated JSON tool protocol remains only as the fallback when a bridge reports no native tools. Production uses the OpenAI API through the `openai_compatible` provider.
8. **Model: `gpt-6.1-sol`.** The harness and prompts are tuned and gated on it (live evals, critical = 100 %); it is the intended production route. Routes stay data in Admin → LLM, never a model name in code.

Also part of the harness: a byte-stable system prompt per bot (`sales-agent@13` retail, `@14` hotel) with every per-turn block on the last user message and `promptCacheKey = <botId>:<conversation>` (OpenAI `prompt_cache_key`, Anthropic `cache_control`, passed through by Hermes); a 100-turn history window with compression at 24 000 chars or more than 30 turns, keeping the last 12 turns, older turns summarised by the bot's tier and stored in `conversation_summaries`; the response lists every delivered message and the loop steps.

## Options considered

1. **Keep the JSON envelope and raise its caps** (more rounds, more images): rejected. The envelope is what made answers stiff (one message, one picture set per turn, format retries and salvage on every malformed answer), and live models handle free text plus tools better than a forced schema.
2. **Run the Hermes Python loop itself (Hermes owns the agent):** rejected. Tools would have to call back into NestJS over the network with tenant credentials, and two systems would decide what the bot may do. Porting the techniques keeps one authority over tenant data.
3. **Queue or steer new customer messages** instead of interrupting: rejected for now. Queueing answers the old message first and then the new one (two replies, the first often outdated); steering (injecting the new message into the running loop) is harder to make safe with writes in flight. Interrupt is Hermes' default `busy_input_mode`.
4. **Keep the number guardrail** on the reply path: rejected by the owner. It replaced correct answers whose figures were phrased differently and could not tell a wrong price from a reformatted one; the eval check keeps the signal without hurting customers.
5. **Only poll faster** instead of LISTEN/NOTIFY: rejected. A short poll costs a query per tick on every agent process; NOTIFY wakes the worker within milliseconds and the poll stays as a safety net.

## Consequences

- Answers can span several messages, each product with its own pictures; a turn may take several model calls (up to 10 rounds). Evals check the delivered messages (joined text, total pictures, per-message counts), and fake-mode cases script model turns (`fake_turns`) instead of an envelope.
- Without the number guardrail, an invented figure reaches the customer unless the prompt prevents it. The `numbers_only_from_sources` eval check and the live critical gate (100 %) are the remaining safety net.
- Prompt changes need live evals on `gpt-6.1-sol`; the Hermes pipe is a development convenience, not a production dependency.
- Migrations (additive): `0037_conversation_summaries` (forced RLS) and `0038_ingress_notify` (the `rapiz_ingress` trigger). The agent process holds one extra database connection for LISTEN.
- Superseded parts: ADR-010's "Hermes has no tools / runtime provider" and ADR-014's JSON final reply (`outcome/reply/sources/imageIds`), 4-round loop, 3-images-per-turn cap and emulated tools as the Hermes path. ADR-014's catalog tools, actions as tools and focus products stand.

Accepted limitations (implementation ledger, 2026-10-31):

- **The re-run happens on the next claim.** An interrupted turn hands its event back (`requeueEvent` keeps it leased for `EVENT_QUIET_MS` + 50 ms, about 0.75 s, so it is never re-claimed alone before the newer message's quiet window has passed); the next claim after that re-runs it with every customer message, instead of re-running in process. This keeps the batching rules and needs no channel-facade change.
- **The carry lives in worker memory.** The interrupted turn's tool work is kept in the agent process (`ResumeStore`, 10-minute TTL). This is correct for today's single agent worker; with several workers, or after a restart, the re-run starts without the carry (it searches again). A multi-worker deployment needs a persisted carry.
- **Billing of an interrupted run.** The AI-message meter is per delivered answer: an interrupted run that already delivered a message (through `send_message`) keeps its charge, and its re-run is charged separately — two real model runs. An interrupted run that delivered nothing is released and its `ai_runs` row has guardrail `interrupted` (not counted as a fallback in the outcome metric).
- **Usage edge case.** `ai_runs` tokens cover every model call of the turn that returned, including the history summarizer and calls before a later failure. A call that throws (aborted by an interrupt, timed out, retries exhausted) records no usage, so tokens a provider may have billed for it are not metered.
- **Mid-turn interrupt eval deferred.** The eval runner drives the playground, which has no interrupt hook or carry, so "a message arriving mid-turn gets an answer covering both" is not an eval case yet; interrupt and carry are covered by the agent-loop and Meta-processor unit tests (tasks 3 and 7).
- **Fallback model: one attempt.** After the primary route's retries, the tier's fallback model gets a single attempt with no empty-answer retry; an empty answer at the deadline is returned as is (the turn then ends in the fallback message).
- **Smaller accepted items.** Comment replies use `fanpage-context@2` (no `send_message`); `sources.used` in the response is a heuristic (the answer quotes the FAQ), not a model citation; a pending action confirmation is cleared when its turn is interrupted or its final answer is dropped (`ReplyResult.askedConfirmation` → `AiFacade.discardPendingConfirmation`; the customer is asked again); a hand-off final is never dropped; pictures carry no explicit S3 host check, because the allowlist only holds the platform's own stored https URLs.
- **A cut-short turn ends with the fallback line.** When a turn stops after it already delivered something (model error, budget or round limit), the bot's configured fallback message is sent last, so a promise such as "em gửi ảnh từng mẫu nhé" is not left hanging. With the default wording this line can follow pictures that were just sent; the wording is the shop owner's setting.
- **Summarizer failure is bounded.** If the history summary cannot be produced, the turn uses the stored summary (if any) plus the newest 30 turns, never the whole 100-turn window.
