# ADR-004: Multi-tenant shared schema + Row-Level Security

- Status: Proposed · Date: 2026-10-23 · Revised 2026-10-23 after independent review (PgBouncer leak, system role)

## Decision

- Every tenant table has `workspace_id`; RLS is **forced** (`ALTER TABLE … FORCE ROW LEVEL SECURITY`) on every tenant table; the application roles do not own tables and have no `BYPASSRLS`.
- Tenant context is **transaction-scoped only**: `select set_config('app.workspace_id', $1, true)` inside an explicit transaction. Plain `SET` is forbidden because the connection pooler runs in transaction mode and a session GUC would leak to the next tenant's request.
- All tenant data access goes through one helper exported by `packages/db`: `withTenant(workspaceId, fn)` — opens the transaction, sets the GUC, runs `fn(tx)`. An ESLint rule forbids importing the raw `db` handle outside `packages/db`. The repository layer **also** filters by `workspace_id` explicitly; RLS is the backstop, not the only gate.
- Policies read the context as `workspace_id = (select nullif(current_setting('app.workspace_id', true), '')::uuid)` — the `(select …)` makes it an InitPlan (evaluated once), `nullif` avoids the empty-string cast error, and a missing context yields **no rows and an application-level assertion** (`withTenant` throws if the GUC is unset after the transaction starts), never silent cross-tenant reads.
- Two database roles with **role-scoped policies**: `app_tenant` (policy `TO app_tenant` with the tenant predicate; API, agent, tenant-scoped jobs) and `app_system` (policy `TO app_system USING (true)`; still no `BYPASSRLS`; every use audited). Processes connect with different login users (`rapiz_tenant` ∈ `app_tenant`, `rapiz_system` ∈ `app_system`). A GUC-based "system mode" is forbidden: any connection could set it. `app_system` is used only by webhook ingress (channel lookup by external id before the tenant is known — via a single `SECURITY DEFINER` function), the scheduler/outbox publisher, nightly reconciliation, analytics rollups and the back-office. The allowed processes are listed in `packages/db/README.md`.
- **Amendment 2026-10-24 (PR #40, owner-accepted):** the Meta inbox added three `app_system` uses not in the list above, accepted as a temporary deviation: (1) `apps/webhook` resolves the connection by `(provider, external_id)` and inserts `channel_webhook_events` in a `withSystem` transaction instead of a `SECURITY DEFINER` function; (2) the public OAuth callback in `api` consumes `channel_oauth_flows` by state hash before the tenant is known; (3) the `agent` process claims, renews, completes, releases and dead-letters `channel_webhook_events` across tenants (ADR-010). Each use touches only those tables, filters by business key, and hands off to `withTenant` for everything else. T-048 narrows them to `SECURITY DEFINER` functions with `EXECUTE`-only grants.
- **Amendment 2026-10-24 (PR #54, for owner acceptance in review):** the analytics projector (T-040) reads `outbox_events` across tenants and writes `analytics_facts`, `analytics_checkpoints` and `analytics_dead_letters` in one `withSystem` transaction under an advisory lock. It runs in the worker and also in the `api` request path: a statistics query first catches the projection up (`ProjectorService.catchUp`) so answers are fresh without waiting for the worker. It reads only the outbox window by indexed `tx_id`, writes only those three tables, and every read that answers a request goes through `withTenant`.
- **Amendment 2026-10-28 (T-078, ADR-012, for owner acceptance in review):** the `account` module reads and writes the global `accounts` and `account_members` tables through `app_system`, because they have no `workspace_id`. They work like `users`. Its repository looks accounts up only by the authenticated user's own membership. It touches only those two tables, and the tenant role has no grant on them. The `account-backfill` operator CLI also runs as `app_system`. It fills `workspaces.account_id` and the new `bot_id` columns across tenants in one transaction.
- **Amendment 2026-11-02 (T-170, ADR-023):** assistant tables are account-scoped; `withAccount` sets `app.account_id` per transaction; same rules as `withTenant`. The four `assistant_*` tables carry `account_id` (not `workspace_id`), force RLS, and give `app_tenant` the policy `account_id = (select nullif(current_setting('app.account_id', true), '')::uuid)`; `app_system` keeps `USING (true)`. `withAccount` throws `withAccount: account context was not applied` if the GUC is unset after it is set.
- **Amendment 2026-11-02 (T-171, ADR-023 lane a, for owner acceptance in review):** the owner assistant's read-only SQL lane (migration 0059). `app_assistant_reader` is a NOLOGIN role with no members that owns the 11 `security_barrier` views of schema `assistant_sql`; it holds column-level `SELECT` grants on the base tables those views read (never phone, email, address, birthday, notes, tokens or settings) and one `FOR SELECT` policy per base table. The policies inline the business predicate: `workspace_id = ANY ((SELECT coalesce(array_agg(w.id), '{}') FROM workspaces w WHERE w.id = ANY (app.assistant_business_ids) AND w.account_id = app.account_id AND w.deleted_at IS NULL)::uuid[])` (the designed `assistant_sql_business_ids()` function was dropped: Postgres runs a function in a policy as the calling login, which would have needed `EXECUTE` and a `workspaces` grant for it, or `SECURITY DEFINER`; the inlined sub-select is checked as the view owner and planned as one InitPlan). `app_assistant_sql` is a NOLOGIN group with `USAGE` on `assistant_sql` and `SELECT` on its views only; its own login (`DATABASE_ASSISTANT_SQL_URL`, created by `migrate --login-roles`, `CONNECTION LIMIT 10`) is a member of nothing else, so there is no role to switch back to. The GUCs `app.account_id` and `app.assistant_business_ids` are set transaction-locally (`set_config(…, true)`) from the owner scope and read back before the query runs. Every query runs in a `READ ONLY` transaction (also `default_transaction_read_only` on the login) with `statement_timeout` 3 s, `lock_timeout` 1 s and `idle_in_transaction_session_timeout` 5 s. The lane runs in `api` only. The login also has the role defaults `temp_file_limit = 256MB`, `work_mem = 16MB` and `track_activities = off` (the first and last are superuser-only, so the login cannot change them, and the runner reads them back). Known gap: the login can read the `PUBLIC` system catalog, including `pg_stat_activity`, but with `track_activities = off` no assistant session publishes its query text there, so another owner's concurrent SQL is not visible; the SQL guard also rejects `pg_*` and `information_schema`.
- Global (non-tenant) tables are explicitly classified in `docs/05` §9 (users, sessions, plans, vouchers, vertical_packs, admin_units, feature_flags, affiliate_*); everything else is a tenant table.
- Connection pooling: PgBouncer ≥ 1.21 in transaction mode with `max_prepared_statements` enabled (or the driver configured with `prepare: false`); no `LISTEN`, no session state, no temp tables.
- CI runs an integration test that executes two tenants' queries sequentially through one pooled connection and asserts isolation, plus a test that a query outside `withTenant` fails.

## Consequences

Defense in depth without a performance cliff (InitPlan policies, `(workspace_id, …)`-leading indexes). Jobs and workers must run inside `withTenant`. A tenant can later be moved to a dedicated database by changing its `tenant_routes` entry (see `docs/17` §6); the code path is the same helper.
