# Meta inbox (Facebook Messenger and Instagram)

Implements CHAT-01 for Facebook Pages and Instagram professional accounts. Other channels in the UI are informational only. Module contracts: `apps/backend/src/modules/channel/MODULE.md`, `apps/backend/src/modules/conversation/MODULE.md`.

**Website chat (T-097..T-104).** The same inbox processor and conversation pipeline also serve the `website` channel ([docs/07](07-channel-integrations.md) section 5). What differs is driven by channel capabilities (`capabilitiesOf(kind)` in `packages/channels`), not by `if (facebook)` checks: Meta kinds have `replyWindowHours: 24`, `website` has `null`, so `withinReplyWindow` never closes the window for a website visitor and staff or the bot can answer at any time. Website delivery is local (the message is stored and the visitor's widget picks it up by polling), so there is no Graph send and no token. Queue event ids are namespaced per visitor (`<visitorId>:<clientMessageId>`).

Post comments and comment-to-private-reply provenance: [Facebook comment automation](integrations/facebook-comments.md) (T-069). Comments use their own persistence and never open the Messenger reply window.

## Flow

1. **Connect.** `POST /channels/{provider}/connect` returns a Meta authorize URL (popup). The callback exchanges the code, lists the granted Pages/accounts as a short-lived discovery, and the user selects which to connect and which bot answers. Tokens are sealed; the app subscribes each Page (`messages`, `messaging_postbacks`, `message_echoes`, `feed`) or Instagram account (`messages`).
2. **Ingest.** `apps/webhook` verifies `X-Hub-Signature-256` on the raw body (`META_APP_SECRET` / `INSTAGRAM_APP_SECRET`), normalizes events (text, HTTPS attachments, echoes) and stores them in `channel_webhook_events`, deduplicated per connection and message id. It never calls an LLM. An `AFTER INSERT` trigger sends `pg_notify('rapiz_ingress', <event id>)`, which wakes the agent worker immediately; a 5 s safety poll (300 ms while the listener is down) covers missed notifications.
3. **Process.** The `agent` entry, on each wake-up or poll tick, claims events with a lease once the customer has been quiet for 0.7 s (a burst is answered together; the oldest message waits at most 4 s, `EVENT_QUIET_MS` / `EVENT_MAX_WAIT_MS` in the channel store), persists every receipt, groups a burst per conversation and asks the AI module for one reply. "Newest" and "already answered" are decided by **receipt order** (claim order = the order we stored the messages), never by Meta timestamps, which can disagree with arrival. The model receives the whole conversation in that order, with all consecutive customer messages after the last bot/staff message merged into ONE customer turn (joined by newlines, attachment notes included once); an outbound message of ANY status (sent, failed, pending, unknown) ends the merge, because a failed reply is still an attempt to answer, so earlier messages are never answered again, and a retry of an event whose reply was already attempted is skipped (never answered or sent twice), so one reply answers every question of the burst; the prompt tells it to answer all of them in order; if the customer writes again while the agent is working, the turn is **interrupted** (agent harness v2, spec §7): the agent loop asks `shouldInterrupt()` before every model call (a newer queued customer event from the same sender, or the bot no longer holds the conversation), stops, and returns its tool work as `carry`; the processor hands the event back (`requeueEvent`, no attempt spent) and keeps the carry in memory for the conversation, so the next claim (as soon as the customer is quiet again) re-runs the turn with every customer message of the burst as one customer turn plus that carry, passed back unchanged. What the interrupted run already sent stays sent and reaches the model through the carry, not as history. A finished answer whose final message is not out yet is dropped the same way when the customer wrote meanwhile; such a re-run has no fresh carry, so everything sent so far is shown to the model as ordinary bot messages. A pending re-run is forgotten when its event is skipped (for example during a takeover) or when staff wrote after it. At most 3 re-runs per burst; the last one runs without an interrupt check and is delivered. A takeover also interrupts, but starts no new turn. A message that still arrives after the answer went out is answered by its own reply, with the earlier reply in context.

   **Bot hand-over (T-053).** When the AI answer is a `handoff` (or a retry-exhausted event, or media the model cannot see), the agent calls `ConversationFacade.handOff`: mode `human` with `autoResumeAt` = now + the bot's takeover window, so the next customer message after the window goes back to the bot (same resume rule as a manual takeover; never resumes when the bot is set not to auto-resume).

   **Messages sent while the agent works (harness v2).** Each turn hands the AI a `MessageSink` (`conversation/application/jobs/reply-delivery.ts`). When the agent calls `send_message`, the message goes out immediately: its text through `splitReply` bubbles (keys `bot:<event id>:s<n>`, `bot:<event id>:s<n>:t2`…, `n` = the send's number in the turn), its pictures as one album (`bot:<event id>:s<n>:img`, then `:img:<index>` per picture when Meta rejects the album, as below). Consecutive sends, the final answer included, are at least 800 ms apart (bubbles of one message go out together). The sink returns how many messages were delivered and returns 0 for good after a takeover, an undelivered message or a newer customer message. The final answer (the `via: 'final'` message) follows as below; an empty final answer after at least one send is fine, and a turn that sent nothing at all gets the bot's fallback message. The first message of the turn, whichever it is, carries the revision check; the turn is billed on its first message with status `sent` (only failed messages, or none, release the reservation; an unsure delivery keeps it until the TTL). Fanpage comment replies get no sink (one public reply per comment) and no interrupt.

   **Chat feel (T-053).** As soon as the bot decides to answer, the agent shows Messenger "seen" then "typing…" (`sender_action`, refreshed every 10 s while the model works; best effort, never retried, never delays the answer). The answer is cut into short bubbles (`splitReply` in `packages/shared/src/reply-split.ts`: at line breaks and sentence ends, at most 4, wording unchanged; the prompt asks for one idea per line; the dashboard test chat shows the same bubbles), sent in order with keys `bot:<event id>`, `bot:<event id>:t2`…; remaining bubbles stop when one is not delivered, the customer wrote again, or a human took over. Consecutive bot bubbles are shown back to the model as one assistant turn. A customer message that gets no reply is never silent: the agent logs the reason (takeover, inactive bot, reply hours, re-auth, or a newer message answering for it).
   - **Customer images (vision, T-053).** When `BOT_IMAGE_VISION` is on (default outside production, off in production unless `true`) and the provider is Hermes, the agent downloads the newest 3 image attachments of the pending customer turn and sends them with the turn (`images` on the AI request, last customer message only). The fetcher (`conversation/infrastructure/media/safe-image-fetcher.ts`) accepts https only, hosts `*.fbcdn.net`, `*.cdninstagram.com`, `lookaside.fbsbx.com`, `cdn.fbsbx.com` (Meta hosts; not re-verified live), resolves DNS itself and pins the connection to a public address, never follows redirects, gives up after 5 s, caps 3 MB per image (6 MB total) while streaming, requires an image/jpeg|png|webp content type that matches the magic bytes, never logs URLs or bytes and never stores them. `BOT_IMAGE_EXTRA_HOSTS` (dev/test, ignored in production) exempts listed hosts from the allowlist and address block and allows plain http for them. Any failure degrades to the text-only behaviour below; if the reply with images fails (for example a provider without vision), the turn is retried once text-only when it has text. An image-only turn goes to the model when at least one image was fetched. Images are customer data sent to the model provider: the ChatGPT-plan login behind Hermes is for testing only.
   - **Attachments without vision.** The model does not see media. A text message that comes with media reaches it with an explicit note in the customer turn (for example `[Khách đã gửi kèm 1 ảnh — bạn không xem được hình ảnh, hãy nói rõ và nhờ khách mô tả hoặc nhân viên sẽ xem]`). If the only unanswered customer content is media (image, file, sticker, no text), the bot sends the bot's `handoffMessage` once and switches the conversation to `human` so staff see it; it does not call the model.
4. **Deliver.** The reply is reserved (idempotency key `bot:<event id>`), re-checked against takeover and sent outside any database transaction. Staff sends use the same path and pause the bot.
   - **Bot pictures (T-053).** When the AI reply carries `images` (customer asked to see a product or library picture; max 3, https URLs from our own stored data only), the agent sends them after the text bubbles as ONE album (a single outbound message whose `attachments` array holds every picture, Meta `message.attachments`; a single picture stays a plain image; empty text, sender `bot`), idempotency key `bot:<event id>:img`. Meta sometimes rejects an album because fetching one picture failed (`#100`, subcode `2018047`, seen intermittently with Shopify CDN images on 2026-10-30); the adapter retries such an album once, and if it is still rejected each picture is sent as its own message (`bot:<event id>:img:<index>`) (`ConversationFacade.commitBotImages`, the same reserve → deliver → record path as the text). They appear in the inbox like any attachment. Pictures are best effort: a failed or unknown send is recorded as its own failed/unknown outbound message, does not stop the next picture, and never fails, retries or hands over the event; a takeover, a deactivated bot or a newer customer message after the text skips the album, and a closed 24-hour window skips them (the text would not have gone out either); a replay of the event is skipped before the AI call, and a repeated key returns the stored message, so pictures are never sent twice. Pictures are sent by URL, so Meta fetches them from the shop's own https host: product pictures must stay publicly reachable.

Before generating, the processor checks the bot is active and inside its reply hours (`replySchedule`, Vietnam time); otherwise the message just waits in the inbox for staff.

On failure an event is retried after 20 s and 60 s; after the third attempt the conversation switches to `human` so staff see it. An event that cannot even be stored in a conversation after its last attempt (or whose worker died) is **dead-lettered**: `processed_at` and `failed_at` are set, the payload is kept for replay, and the agent logs an error (UI for dead letters: T-049). While a page awaits re-auth (`reauth_required`), inbound messages are still stored for staff; the bot does not reply until the page is reconnected.

- **Tích hợp nền tảng** (`/app/channels`): platform list (all, waiting for a bot, Facebook, Instagram; Zalo, Lazada and TikTok marked as coming soon) and the page list with search, select all, explicit bulk bot assignment, bot/unassigned filtering and confirmed unassignment (which preserves provider connectivity) and connect. Message sync is not supported and the button is disabled. Each Facebook/Instagram page card has a "⋯" menu with **Gỡ trang**, and the toolbar has a bulk **Gỡ trang** next to "Hủy gán bot"; both ask for confirmation and are shown only to users with `settings.manage` (see "Removing a page" below). Website chat cards are not removable from here.
- **Bot → Tích hợp** (`/app/bots/{botId}/integrations`): only pages bound to that bot. "Chỉnh sửa" chooses which workspace pages the bot answers; "Hủy kích hoạt" unbinds them (`botId: null`). Pages connected from here are bound to the bot right after selection.
- **Tin nhắn đa kênh** (`/app/inbox`): Meta Business Suite layout (T-096) — channel tabs, conversation list with quick and advanced filters and bulk management, thread with takeover controls and attachments, customer panel. See [Sales inbox workspace](18-sales-inbox-workspace.md).

**Permissions.** When `META_LOGIN_CONFIG_ID` is set, the Facebook Login for Business configuration decides the permissions (the app does not send `scope`, or Meta answers "Invalid Scopes"). The configuration must include `pages_show_list`, `pages_messaging` and `pages_manage_metadata` (comment automation additionally requests `pages_read_engagement`, `pages_read_user_content` and `pages_manage_engagement`; basic messaging does not require these additional grants); a missing one fails the connection and the API log names it. Meta's own error code, subcode and `fbtrace_id` are logged for every rejected Graph call. The Facebook user token is exchanged for a long-lived one before the Page tokens are read, so Pages do not need reconnecting after about an hour.

Register webhooks on the Meta app for object `page` → `${META_APP_ORIGIN}/webhooks/facebook` and object `instagram` → `${META_APP_ORIGIN}/webhooks/instagram`. While the Meta app is in development mode, only people with a role on the app (administrator, developer or tester) can connect and message. Anyone else — or everyone, when Meta has restricted the app (for example an overdue Data Use Checkup or missing privacy policy URL) — sees Facebook's "App not active" page in the login popup; fix it in the Meta App Dashboard, not in code.

One HTTPS tunnel can serve the whole stack through `scripts/dev-tunnel-proxy.mjs` (port 4000): `/api/*` → API (3000), `/webhooks/*` → webhook ingress (3001), the legacy `/api/channels/oauth/*` redirect → `/api/v1/channels/oauth/*`, everything else → Vite (5180).

```bash
cd apps/backend && pnpm exec tsx watch --env-file-if-exists=../../.env src/entries/agent.ts
cd apps/webhook && PORT=3001 pnpm exec tsx watch --env-file-if-exists=../../.env src/main.ts

```

Open the app through the tunnel URL (not `localhost`) so the OAuth popup can return its result.

## Trying the bot end to end on a fresh checkout

1. `cp .env.example .env`, fill the Meta variables above, `SECRETS_ENCRYPTION_KEY` and `HERMES_BRIDGE_KEY` (32+ characters). Database and role names are `rapiz` / `rapiz_tenant` / `rapiz_system`; a database created before the Rapiz rename must be recreated, then `pnpm db:migrate:dev`.
2. Start the API, agent and webhook ingress as in "Local live testing", plus the Hermes bridge (`services/hermes/README.md`).
3. Sign up in the web app, then make that user a platform admin: `pnpm --filter @agent-sales/backend platform-admin grant <email>`.
4. Admin → LLM: add a `hermes` provider (base URL `http://127.0.0.1:8788`, key = `HERMES_BRIDGE_KEY`), press "Đăng nhập ChatGPT" and approve the code, choose a model from the list in each plan's route, and press "Kiểm tra".
5. Create a bot (fill the mission, products, FAQs, situation instructions), connect a Page on Tích hợp, bind it to the bot and turn the bot on. Send a message from an account that has a role on the Meta app.

Images: customers' pictures are read by the model when `BOT_IMAGE_VISION` is on (default outside production), and the bot sends product pictures (up to five https URLs per product) when asked. The ChatGPT-plan sign-in is for testing only and is off in production.

## Inbox v2 data and API (T-073)

Design: `docs/superpowers/specs/2026-10-25-inbox-v2-design.md`. A conversation is still one `data jsonb` document, plus index columns derived from it on every save (migration `0024_inbox_v2.sql`): `unread_count`, `awaiting_since`, `last_read_at`, `assignee_id`, `mode`, `status`, `customer_phone`, `created_at`. The list filters, counts and sorts in SQL on those columns.

| Field | Meaning |
|---|---|
| `unreadCount`, `lastReadAt`, `lastReadBy` | Read state **shared by the whole shop**. A customer message adds one; `POST /conversations/{id}/read` clears it and records who; `POST /conversations/{id}/unread` sets it to at least 1 and forgets the reader. Neither bumps `revision` or `updatedAt`, so a pending bot reply stays valid and the list does not reorder. |
| `awaitingSince`, `lastMessageSender` | "Customer is waiting": set by a customer message while null (to the message time), cleared by any outbound message (staff in the app, staff on the page, or the bot). A reply that fails to send restores it. The waiting tab, `counts.waiting`, the `waiting=*` filters and `sort=waitingLongest` count only **open** conversations; a resolved one keeps `awaitingSince` and returns when reopened. |
| `customerPhone` | First Vietnamese mobile number found in a customer message (`0xxxxxxxxx`, `+84…`, `84…`; one consistent separator style of space, dot or dash; landlines, dates, prices and order codes ignored). Later messages never overwrite it; staff correct it with `PATCH { customerPhone }` (a phone string, validated and normalised, or `null`). |
| `notes[]` | Internal notes timeline (author, time, text; at most 200, oldest dropped). `POST /conversations/{id}/notes`. The legacy `note` string is migrated as the first entry and mirrors the newest note; `PATCH { note }` with a changed non-empty text also appends a timeline entry, and an empty `note` only clears the legacy field. |
| `contactId` | The CRM customer (T-088, column `contact_id`). Set by the first phone number a Facebook/Instagram customer sends (find-or-create by E.164 phone through `CrmFacade.upsertLeadByPhone`, source `facebook`/`instagram`; best effort, never fails the message), by a website lead, or by staff with `PUT /conversations/{id}/contact { contactId \| null }` (`contacts.edit`; a customer of another business answers 404). Staff choice wins: automatic linking never replaces an existing link. Each bot answering a linked conversation is recorded on the customer (`recordContactBot`). |
| `assigneeId` | `PATCH /conversations/{id}` accepts any active member (checked through `TeamFacade`) or `null`; `assignToMe` still works. |

`GET /conversations` query: `tab` (`all|unread|waiting`), `assignee` (`me|none|<uuid>`), `channelId`, `contactId`, `botId` (`none|<uuid>`: the bot answering now), `updatedFrom` / `updatedTo` (ISO instants with offset; last activity, `from` inclusive and `to` exclusive, `from` must be before `to`), `hasPhone`, `waiting` (`any|longest|readNotReplied`), `status`, `mode`, `provider`, `q` (name, phone, customer id, last message), `sort` (`recent|waitingLongest`), `limit`. The response carries `counts: { all, unread, waiting }` computed with every filter except `tab`.

Deploys of migration 0024 and the new store must be atomic: code from before it writes only `data`, which would leave the columns (and so the list, tabs and counts) stale. The migration is re-runnable (values the document already carries are kept, malformed ones become null/0). Backfill of existing rows: columns come from the document; `awaiting_since` is the first customer message after the last outbound one for open conversations whose newest message is the customer's; `unread_count` starts at 0 (no history of who read what); `customer_phone` starts empty and fills from new messages.

**Takeover and sender name.** `PATCH { mode: 'human', takeover: 'temporary' | 'permanent' }` (`takeover` only with `mode: 'human'`). `temporary` resumes the bot after the bot's `humanTakeoverMinutes` when the channel has an active bot that resumes after manual replies; `permanent` (or no `takeover`) never resumes, and staff replies or Page echoes on it do not start the timer. A staff reply or echo while the bot answers is an implicit `temporary` takeover. `mode: 'bot'` clears it (`takeover: null`). Messages sent by staff from the inbox carry `senderName` (their display name); bot, customer and echo messages carry `null`.

### Work folders, star and bulk actions (T-096)

| Field / route | Meaning |
|---|---|
| `status` | Work folder: `open` (the queue), `resolved` (Done) or `spam`. A customer message reopens Done (`status: open`, unread +1) but leaves Spam in Spam (unread still counts, never waiting). Only `open` conversations take replies: the bot already required it, and a staff `POST /conversations/{id}/messages` on Done or Spam returns `409 CONFLICT` until staff reopen it (`PATCH { status: 'open' }`). A retry with an already reserved idempotency key still returns the original message. Restoring sends nothing. |
| `starred` | Follow / priority flag (Meta's "Ưu tiên"), default `false`, `PATCH { starred }`. Independent of read state and folder. Like read state it is an annotation: a star-only change (PATCH with just `starred`, or bulk `star`/`unstar`) bumps neither `revision` (a queued bot reply stays valid) nor `updatedAt` (no reordering). Stored in the document only (no index column, no migration). |
| `GET /conversations` | Also accepts `status=spam`, `starred=true|false` and `followUp=true|false` (a follow-up reminder is set / not set). Counts keep their rule: every filter except `tab`. |
| `POST /conversations/bulk` | `{ action, ids, assigneeId? }`, at most 100 ids, `contacts.edit`. Actions: `resolve`, `reopen`, `spam`, `star`, `unstar`, `read`, `unread`, `assign` (needs `assigneeId`, a member or `null`), `clearFollowUp`. Each id runs the single-conversation path in its own transaction (same audit event, revision bump and checks); the response is always 200 with `{ data: [{ id, ok, code }], succeeded, failed }` in request order; an unexpected failure is logged and reported as `INTERNAL` for that id only. An id of another workspace is `NOT_FOUND`. The assignee is validated once before anything changes. No action sends a message. |

Since T-096 control changes (folder, assignee, follow-up, reply mode, bot hand-off) bump `revision` but no longer `updatedAt`: the list is ordered by conversation activity (customer messages, replies, echoes) and a row's time stays at its last message (INB-LST-04).

### Conversation tags and tag filters

Conversations use the CRM tag library (`crm_tags`) and `crm_tag_assignments` with `scope = 'conversation'`, owned by the crm module.

| Route | Notes |
|---|---|
| `GET /conversations/{id}/tags` | Active tags, each with its chip (`tag: { id, name, color }`). |
| `POST /conversations/{id}/tags` `{ tagId, values? }` | 201 when added, 200 when already there. Needs `contacts.edit`. |
| `POST /tag-assignments/{id}/remove` | The existing route; idempotent. |

List rows and detail carry `tags: [{ id, name, color }]` (oldest assignment first, archived tags hidden). The list accepts `tagsAny`, `tagsAll`, `tagsExclude` (comma-separated or repeated uuids) and `untagged=true`; the conversation module asks `CrmFacade.conversationIdsByTags` for id sets and applies them in its own SQL, so the counts follow the tag filters. Conversation tags publish no `crm.tag.*` event and never count as customer tags.

### Customer profile lookup

After a customer message the agent asks the channel module for the customer's name and picture (`ChannelFacade.fetchCustomerProfile`; the page token never leaves the channel module). Messenger: `GET graph.facebook.com/{version}/{psid}?fields=first_name,last_name,profile_pic,name`. The full `name` is preferred (outer spaces trimmed, order and middle names kept, 200-character bound); `first_name` + `last_name` is only the fallback when `name` is missing or blank, because the joined parts can drop middle names or use another order (seen on the owner's own test conversation, 2026-10-29, T-136). Instagram: `GET graph.instagram.com/{version}/{igsid}?fields=name,username,profile_pic`, falling back from name to username (written from the docs on 2026-10-25, not yet run against a live account). Both send the token in the `Authorization` header (official docs: [Messenger user profile API](https://developers.facebook.com/docs/messenger-platform/identity/user-profile) and [Instagram messaging user profile](https://developers.facebook.com/docs/instagram-platform/instagram-api-with-instagram-login/messaging-api)). The call runs after the message is stored and is not awaited by the reply pipeline. The attempt is stamped in `profileFetchedAt` before the call; a failed lookup (network, 5xx, timeout, refusal) is retried after 15 minutes, a success after a day; a success is refreshed daily as well because Meta picture URLs expire. Failures are ignored and never logged with the customer id. The conversation's `revision` and `updatedAt` do not change.

## Connection lifecycle and removing a page (T-133)

`channel_connections.status` is one of `connected`, `reauth_required` (token expired: inbound is stored, sending is blocked), `disabled` (website chat switched off), `disconnected` (legacy `PATCH {disconnect:true}`: no bot, no ingestion, still listed) and `removed`.

`DELETE /api/v1/channels/{id}` (204, `settings.manage`, other workspace -> 404) **soft-removes** a Facebook or Instagram page:

- The row is kept with status `removed`, `bot_id = null` and the sealed page token replaced by a sealed empty value, so no credential stays behind. Conversations, messages, comments and statistics are untouched.
- `GET /channels` (integrations page, bot readiness) no longer returns it. The inbox asks for `GET /channels?includeRemoved=true` so old conversations keep their page name; the inbox page filter leaves removed pages out, and such a conversation stays readable with a notice instead of a composer. A reply attempted anyway fails with `failureCode: page_removed` (not `reauth_required`).
- Facebook only: best-effort `DELETE graph.facebook.com/{version}/{page-id}/subscribed_apps` with the page token in the `Authorization` header (8 s timeout), sent after the removal is saved so a failed save leaves the page connected and subscribed. Any failure (expired token, network, Meta refusal) is ignored for the removal; only Meta's numeric error code and subcode are logged. Instagram pages are not unsubscribed (no matching endpoint is used by the connect flow); ingress already drops their events. This partially addresses T-049 ("page release on disconnect"); releasing the page for another workspace is addressed by T-142 below; purging stale OAuth flows remains open there.
- `apps/webhook` stores events only for `connected`/`reauth_required` connections, so a removed page receives nothing new. Events queued before removal are rejected by `ConversationFacade.receive` (`removed` is refused like `disconnected`) and do not create conversations or messages.
- Reconnecting the same page through the normal OAuth flow in the same workspace restores that workspace's own removed row (same id, so its history stays attached) and sets it back to `connected` (bot not restored: assign it again), as long as no other business holds the page live.
- **Moving a page to another business (T-142).** Only live rows own a page: the unique index `channel_connections_live_external_key` is on `(provider, external_id) WHERE status <> 'removed'` (migration `0034_channel_reconnect_elsewhere.sql` replaces the old unconditional unique constraint). A page removed in business A can be connected in business B through OAuth discovery: B gets a NEW row, A's row stays `removed` with its id, conversations and statistics. A live row (any non-`removed` status) in another business still blocks with "connected to another workspace", and the database cannot hold two live rows for one page. The upsert targets the partial index (`ON CONFLICT (provider, external_id) WHERE status <> 'removed'`); a removed row of the same business is revived first, guarded by a savepoint so a live row elsewhere yields the same conflict error. Webhook ingress and the website lookup resolve a page id to the live row only. Migration 0034 is backward compatible: existing data has at most one row per page, so the index builds; **deploy order: run migration 0034 before starting the new API.** Old API instances still target the dropped unconditional constraint (`ON CONFLICT (provider, external_id)`), so once the constraint is gone they fail every page connect until they are replaced; the drop is `IF EXISTS`, so a re-run is safe.
- Website chat is excluded: `DELETE` on a website connection is a validation error (use enable/disable or "Xóa kết nối").
- Migration `0033_channel_removed_status.sql` only widens the status CHECK constraint. Run it before deploying the new API; API instances from before T-133 cannot parse a `removed` row in `GET /channels`.

## Limits

- Outbound attachments are sent by HTTPS URL (bot image library, a product's `imageUrls` or a pasted link); there is no file upload to Meta. Product pictures are plain https links entered in the product form (max 5, 2000 characters each); there is no upload or reference to the image library yet.
- Meta CDN attachment URLs expire; the inbox shows them as received and falls back to a link.
- A customer's name and picture come from a best-effort profile lookup (below); until it succeeds, `customerName` is the Meta-scoped id and the UI shows a masked label.

## Inbox tag values (T-090)

Tags use the Customer settings library and conversation-scoped CRM assignments. Tags without active fields attach in one click; tags with active fields open the same values editor used by CRM. Required fields must be filled before assignment; numeric zero and boolean false are valid values. Archived fields are not requested. Failed saves keep the form and entered values available for retry; leaving the conversation discards an unfinished form. Quick attach/remove actions wait for an in-flight mutation. These changes do not merge customer tags with conversation tags or alter tag ownership.

## Page assignment and navigation (T-082, T-083)

Global platform integrations is a single top-level navigation destination at `/app/channels`. Each bot retains `/app/bots/:botId/integrations`, named Channel integrations (Tích hợp kênh, T-114), with a link back to the inventory. Select eligible pages and choose an actual bot before saving; moving pages away from another bot requires confirmation. Unassign bot clears only botId and keeps the connection and message history. Connectivity and bot assignment are independent labels and filters. Failed bulk rows remain selected for retry; successful rows are not replayed. Discovery selection, bulk assignment and single updates refresh channel, bot-readiness and inbox queries. The available providers remain unchanged.

This slice uses existing workspace/bot contracts. Shop fields, shop eligibility and cross-shop filters remain pending lane A's approved hierarchy (T-077/T-078/T-080); T-082 is not complete until that integration is accepted.
