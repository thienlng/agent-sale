# assistant

**Purpose:** the owner assistant "Thỏ Rapiz" (ADR-023, T-170): an account owner's private chat threads, the runs that answer them and their steps. Owner-only and account-scoped, not business-scoped.

**Owned tables:** `assistant_threads`, `assistant_messages`, `assistant_runs`, `assistant_run_steps` (migration 0056), `assistant_memory`, `assistant_proposals` and the compaction columns (`assistant_threads.cache_root_id`, `compacted_at`, `compaction_failed_at`, `compaction_saved_pcts`; `assistant_messages.sort_seq`) (migration 0057), `assistant_skills`, `assistant_skill_events`, `assistant_suggestions`, `assistant_settings`, `assistant_jobs`, `assistant_messages.feedback` and the review counters (`assistant_threads.review_owner_turns`, `review_tool_rounds`, `last_review_at`) (migration 0058); schema in `packages/db/src/schema/assistant.ts`. Every row carries `account_id`; RLS reads `app.account_id`, set by `withAccount`. `assistant_messages.search` (generated tsvector, GIN + trigram indexes) exists only in SQL and is queried with `sql`. Only the worker's `claimJobs` and `ownersWithLearnedSkills` read across accounts, on the `app_system` connection (`withSystem`); the worker's other calls pass the claimed job's account and owner and stay under `withAccount`.

**Public API (`api/`):**

- `ASSISTANT_FACADE` → `AssistantFacade.listThreads | createThread | updateThread | listMessages | sendMessage | getRun | getMemory | deleteMemoryEntry | listProposals | approveProposal | rejectProposal | listSkills | getSkill | createSkill | updateSkill | deleteSkill | approveSkill | rejectSkill | archiveSkill | restoreSkill | shadowSkill | listSkillEvents | undoSkillEvent | getLearning | getSettings | updateSettings | setMessageFeedback | listSuggestions | acceptSuggestion | dismissSuggestion` (actor = user + current business; `sendMessage` and `approveProposal` also take the caller's `Authorization` header, held in memory only; `sendMessage`'s actor may carry a lazy `displayName`, read only when the turn compacts the thread). No other module consumes it yet.
- `ASSISTANT_RUNNER` → `AssistantRunner.tick()`: the worker entry ticks it every 15 s (background jobs, below).
- HTTP (`assistantRoutes`, all `@WorkspaceScoped()`, all `assistant: never`): `GET/POST /assistant/threads`, `PATCH /assistant/threads/{threadId}`, `GET/POST /assistant/threads/{threadId}/messages`, `GET /assistant/runs/{runId}`, `GET /assistant/memory`, `GET /assistant/learning?days=7` (1–30; the learning feed, below), `DELETE /assistant/memory/{store}/entries/{entryId}`, `GET /assistant/threads/{threadId}/proposals`, `POST /assistant/proposals/{proposalId}/approve|reject`, and the skill routes (1c, below): `GET/POST /assistant/skills`, `GET /assistant/skills/{skillRef}`, `PATCH/DELETE /assistant/skills/{skillId}`, `POST /assistant/skills/{skillId}/approve|reject|archive|restore`, `POST /assistant/skills/platform/{name}/shadow`, `GET /assistant/skills/{skillId}/events`, `POST /assistant/skill-events/{eventId}/undo`, and (1c, `interface/http/assistant-settings.controller.ts`) `GET/PATCH /assistant/settings`, `POST /assistant/messages/{messageId}/feedback`, `GET /assistant/suggestions`, `POST /assistant/suggestions/{suggestionId}/accept|dismiss` (below). `POST …/messages` runs one chat turn (below) and answers 200 with the turn's visible messages and its run; 409 `CONFLICT` (`details.reason = assistant_busy`) while another run of the owner is running, or for a retried `turnId` whose run is still running, or (`turn_id_taken`) when the `turnId` is another owner's run or a run of another thread; 503 `AI_UNAVAILABLE` when no model serves the `pro` tier. `GET /assistant/memory` lists owner_profile, notes, then one `business:<id>` store per business of the account the owner is a member of (by id), empty ones included, each with `label` (English key, or the business name), `limit` and `used`; `DELETE …/entries/{entryId}` answers 200 with the remaining memory, 404 for an unknown store or entry.
- Events: none.

**Depends on:** `account` (`listForUser`: owner role), `workspace` (`accountOf`; `listMemberships` for `scope.businessIds`, the prompt's business list and the memory labels, read once per request and reused through `accountMemberships`), `ai` (`AI_LLM_GATEWAY` for chat turns, `isAiNotConfiguredError` to answer 503). The SQL lane reads the `assistant_sql` views of `packages/db` on its own login: `DB_ASSISTANT_SQL` (from `common/db`, null without `DATABASE_ASSISTANT_SQL_URL`) is used only by `infrastructure/sql/postgres-sql-runner.ts` behind the `ASSISTANT_SQL_RUNNER` port (below); this is the one read path to other modules' data outside their routes (ADR-023, ADR-004 amendment T-171). Otherwise other modules' data is reached only through their declared HTTP routes (`ROUTE_INVOKER` → `infrastructure/http/fastify-route-invoker.ts`, Nest `HttpAdapterHost` + Fastify `inject` on `/api/v1`), never their internals.

**Chat turn (`application/chat-turn.service.ts`):** `startRun` (id = `turnId`, tier `pro`, the thread's prompt version) → store the owner's text (raw, with its `pageContext`) → `CompactionService.maybeCompact` with the thread's last finished chat run (any error is logged and the turn goes on with the full history) → history = all active messages by `sort_seq`, safety-capped at the last 200 and starting at a user, event or summary message (a tool call never loses its results) (`event` rows as `[event] …` user messages); only the last user message is sent as `buildTurnMessage` (`<page_context>` JSON, `<current_business>` = the current business id, `<current_time>` HH:mm in Asia/Ho_Chi_Minh, then the text) → `runAgentLoop` on `AI_LLM_GATEWAY` with the core, memory, skill and route tools (definitions sorted by name), all wrapped once by `withTurnOutputBudget` (`application/turn-budget.ts`: one 40 000-char counter per turn over every tool result and every validation error the loop writes for bad arguments; the result that crosses the limit is cut to what is left, later calls answer `{ok:false,errorCode:'turn_budget_exhausted'}` without running), at most 25 rounds and 90 s (less the time a compaction took, at least 30 s), 60 s per model call, an owner-facing wrap-up notice at 80 %, `promptCacheKey = asst:<owner>:<cache_root_id ?? thread>` (stable: the root is the thread id) → store the tool exchange (hidden) and the answer with the turn's `uiActions` (`finalUiActions`: the last navigate, the last fill_form, up to 3 charts in call order, then the last spotlight; none when the turn did not answer) → `finishRun` (usage, rounds = model calls, latency, provider/model). Steps are written as they happen (kind, tool name, ok, ms; never arguments or results). No answer text, or an outcome other than `done`, gives the fallback reply; a model error gives the fallback reply too, with the run `failed` (`guardrail = model_error`). An untitled thread takes the first 60 characters of its first message as its title. Logs carry the run id, tool name and error class only.

**Core tools (`application/core-tools.ts`, results ≤ 8 000 chars):** `session_search({query, limit≤10=3})` over the owner's earlier user/assistant messages; `ui_navigate({to})` only for `/app` or `/app/…` by the same rule as the web app's `safeAppPath` (decoded until stable, no `%`, query, hash, backslash, `//`, control character or dot segment; ruling R6), else `invalid_path`; `ui_spotlight({target, hint})` only for a target listed in the page context, else `unknown_target`. `ui_fill_form({formId, values})` drafts values into a form the page context lists: `formId` must be one of `page.forms[].id` (`unknown_form`), every key a declared field (`unknown_field:<name>`), a `select` value one of its options (`invalid_option:<name>`), strings ≤ 4 000 chars (`too_long:<name>`), at least one value (`no_values`); it answers "filled as a draft; the owner reviews and saves it themselves" and never submits. The UI tools add to the answer's `uiActions`; none of them changes data.

**Memory tool (`application/memory-tools.ts`):** `memory({action: add | replace | remove, store, text≤1000, match≤200})`. Stores (`domain/memory-store.ts`): `owner_profile` 1 400, `notes` 2 200, `business:<id>` 1 000 chars (used = sum of entry lengths); a business store must name one of `scope.businessIds`, else `unknown_store`. `add` needs `text`, `replace` needs `match` and `text`, `remove` needs `match` (`missing_text` / `missing_match`); `match` must be a substring of exactly one entry (`match_not_found` / `match_not_unique`); exact duplicates are `duplicate`; new text goes through `scanUntrustedText` (`unsafe:<issues>`) and is folded to one line; a write past the limit answers `store_full` with the entries and "consolidate: replace or remove entries first". After 3 failed calls in a turn every further call answers `stop_retrying`. Success: `{ok, message, used, limit}`. Memory text is never logged.

**Route tools (`application/route-catalog.ts`, `route-tools.ts`, spec §6):** the catalog is built once from `allRoutes`: workspace-scoped routes whose `assistant.use` is `read` (a GET, or a POST flagged `queryPost`, ruling 1b-R7) or `write` (never a GET); a missing field is unusable and `/assistant`, `/auth` routes are excluded whatever they say. Entries are keyed `METHOD /path`. Every `when` text is English, so the `tool_search` description tells the model to query in English words. `tool_search({query})` → the top 8 `{key, use, summary, when}` by word overlap (unaccented, lowercased, plural `s` folded) with key, summary and `when`, boosted when the route's first path segment is the page's `/app/<section>`. `tool_describe({key})` → `{key, use, pathParams, query, body}` (JSON schema, `io: input`, ≤ 8 000 chars) or `unknown_key`. `tool_call({key, businessId?, params?, query?, body?, summary?})`: `businessId` defaults to the current business and must be in `scope.businessIds` (`unknown_business`); every path param must match `^[A-Za-z0-9_-]{1,64}$` (`bad_params`); query (as strings) and body are checked with the route's Zod schemas (`invalid_input` + first 5 issues). A **read** runs through `ROUTE_INVOKER` with the owner's own bearer token, `X-Workspace-Id` = the business and `X-Actor: assistant`, so the real auth guard, capabilities and RLS apply; the result `{status, body}` is ≤ 8 000 chars (`…[truncated]`) and `tool_call` results also keep their own 40 000-char read budget per turn (`turn_budget_exhausted`), inside the turn-wide budget above; HTTP ≥ 400 → `http_<status>` (403 adds "Tài khoản của anh/chị không có quyền này"). A **write** never runs: it needs `summary` (`summary_required`), a body of at most 20 000 chars as JSON (`body_too_large`) and fewer than 20 unexpired pending proposals in the thread (`too_many_pending`), and becomes a pending proposal (expires in 24 h) whose `preview` is `{body, query}` plus, for PATCH/PUT/DELETE with a GET on the same path, `before` (the current state, read with the owner's token); the result is `{status: 'awaiting_owner_approval', proposalId}`. `tool_call` is not read-only for the loop, so calls run in order. The bearer token lives in the turn's memory only: never stored, logged or put in a step.

**SQL lane (T-171, `application/sql/`, `domain/sql-guard.ts`, `domain/ports/sql-runner.port.ts`, `infrastructure/sql/postgres-sql-runner.ts`):** `sql_schema` and `sql_query` are **native entries** of the deferred catalog (ruling 2-R5), toolset `sql`: not in the tool list; `tool_search` scores them with the route entries (same words, no page boost, `use: 'read'`), `tool_describe` returns `{key, use: 'read', pathParams: [], body}` (JSON schema of the input), and `tool_call({key, body})` validates `body` with the entry's input (`invalid_input` + first 5 issues), ignores `businessId`/`params`/`query`, and counts the result against the 40 000-char read budget. Native keys are checked before route keys. They exist only when `ASSISTANT_SQL_RUNNER` is not null (`DATABASE_ASSISTANT_SQL_URL` → `DB_ASSISTANT_SQL` in `common/db`) and `sql` is not in the owner's `disabledToolsets` (1c settings; the 1c toolset list itself is not built yet, so `sql` is registered only here). `sql_schema({view?})` → the rules and one line per view (< 6 000 chars), one view with column types and examples, or `unknown_view`; the catalog (`sql-views.ts`) matches `information_schema.columns` of `assistant_sql` (integration test) and every example passes the guard. `sql_query({sql ≤ 4 000, businessIds? ≤ 50, chart?})`: the 9th call of a turn answers `sql_query_limit`; then `checkSql` (`sql_rejected` + reason, nothing runs); `businessIds` default to `scope.businessIds`, any other id is `unknown_business`; then the runner. `SqlRunError` maps to `sql_timeout` (57014), `sql_permission_denied` (42501), `sql_unknown_name` (42P01/42703), `sql_unavailable` (class 08) or `sql_error`, with `sqlstate`, the message cut to 300 chars and a hint. Success: `{ok, columns, types, rows, rowCount, rowsShown, truncated}` with string cells cut to 200 chars and the JSON ≤ 8 000 chars (rows dropped from the end, plus `note`), `<` escaped. **Charts** (`application/sql/chart.ts`, ruling 2-R6): `chart: {kind: bar|line|pie, title, x, y[1..4], unit?, labels?}` names result columns only; `buildChart` uses the **full** fetched rows (not the cut model view) and keeps only the x and y columns (x cells as text ≤ 80 chars, y numbers or null; labels default to the column name, cut to 60; unit defaults to `number`). Errors `chart_unknown_column:<c>`, `chart_duplicate_column:<c>`, `chart_reserved_column:__proto__`, `chart_not_numeric:<c>`, `chart_needs_full_result` (truncated), `chart_empty`, `chart_too_many_points` (> 60 rows, a pie > 12), `chart_bad_pie` (not one y, or a negative value), and `chart_limit` from the 4th chart of a turn; a chart error never fails the call (`ok: true` with `chart: {errorCode}`). On success the `chart` UI action is pushed to the turn and the result says `chart: 'shown'`. The answer stores it in `ui_actions`, and the web bubble renders it with a lazy recharts chunk. `PostgresSqlRunner` runs the guard **again** before `runAssistantSql` (one `READ ONLY` transaction; scope GUCs, `statement_timeout`, `idle_in_transaction_session_timeout` and the read-only flag set transaction-locally and read back, with the login's `temp_file_limit` and `track_activities`), maps class 08 and errors without a SQL state to `SqlRunError('08000', 'unavailable')`. Logs carry the error code, SQL state, run id and a fingerprint (`sql=<sha256:12> len=<n>`), never the SQL text or rows. 1c's usage counter counts SQL calls under `routes` (the step tool name is `tool_call`). Limits: 3 s statement, ≤ 500 rows (501 fetched), ≤ 8 000 chars to the model, ≤ 8 queries and ≤ 3 charts per turn, pool 4. The guard allows no string-building operator or function (`||`, `concat`, `replace`, …), caps string literals at 200 chars and CTEs at 10; the login's role defaults `temp_file_limit = 256MB`, `work_mem = 16MB` and `track_activities = off` bound memory and hide query text from `pg_stat_activity` (final review C1, I1; `runAssistantSql` reads the first and last back). The `answer-data-questions` platform skill teaches the flow; `read-revenue` (v2) points to it and falls back to the sales overview route when the lane is off.

**Proposals (`application/proposals.service.ts`):** list = expire stale pending proposals, then the thread's proposals oldest first. Approve/reject: the proposal must be the owner's and its business still in `scope.businessIds` (else 404); stale ones expire first. Approve = `transitionProposal(pending → executing)` (the atomic guard; null → 409 `proposal_not_pending`, or `proposal_expired` when it expired; one that expired since is moved to `expired` → 409 `proposal_expired`), then the stored `route_key` is looked up in the current catalog (no longer a `write` → `failed` with `route_not_allowed`, nothing runs), then the stored request runs on the proposal's own `businessId` (as `X-Workspace-Id`, whatever business the approving request names) with the **approver's** token and `Idempotency-Key: asst:<id>`. The key is sent but not enforced server-side yet (no route deduplicates on it), and `X-Actor: assistant` is sent but not audited yet (the change is recorded as the owner's own request); the atomic `pending → executing` transition is what prevents a double execution; 2xx → `done` with `resultPreview` (≤ 1 000 chars), else `failed` with `http_<status>` (`invoke_failed` when the call threw). Reject = pending → `rejected`. A proposal row stores the owner's own request (`path`, `query`, `body`), the `preview` with the `before` snapshot, and a `result_preview` of at most 1 000 chars: the owner's own data on an account-scoped row behind RLS (ruling 1b-R10), the only business data the assistant keeps. Each decision appends an `event` message (`Đã áp dụng: …`, `Không áp dụng được: … (<code>)`, `Anh/chị đã bỏ: …`), so the next turn sees it.

**Compaction (`application/compaction.service.ts`, spec §9):** skipped during the 10-minute cooldown after a failure (`compaction_failed_at`), and when the last two `compaction_saved_pcts` are both < 10 (anti-thrash) unless 24 h have passed since `compacted_at` or the thread has more than 160 active messages. Due when `shouldCompact` says so: the last finished chat run's `(input_tokens + cached_tokens) / rounds` (runs store usage summed over their model calls, so the per-call average stands in for the last call) ≥ 75 % of (`ASSISTANT_CONTEXT_TOKENS` 128 000 − `ASSISTANT_MAX_OUTPUT_TOKENS` 16 000), or more than 80 active messages. Then `planCompaction` (null → nothing) and one summariser call on tier `basic` (`buildCompactionPrompt`, the previous summary updated, 30 s cap, same `promptCacheKey`), recorded as an `assistant_runs` row of kind `compaction`. The summary row (role `user`, `is_summary`) is `COMPACTION_SUMMARY_PREFIX` + the text + the thread's pending proposals (`- <summary> (id: <id>)`); the thread's system prompt is rebuilt (`ThreadPromptService`: businesses, skills index and a fresh memory snapshot, the thread's own prompt version); `savedPct` = 1 − chars after / chars before over the active messages; `applyCompaction`. `planCompaction` lists for pruning the tool results longer than 200 chars that stay active: in the head, and in the tail except its last 10 messages (ruling 1b-R11); summarised rows are never listed. Any failure before the save (model error, empty summary, stale plan) calls `markCompactionFailed` and keeps the history; a failed read-back after a saved compaction does not (the turn uses the thread as just saved). The summary is for the model only: `isVisibleMessage` hides it and search skips it.

**Skills (`application/skill-catalog.ts`, `skill-tools.ts`, `skills.service.ts`, `skill-manage.ts`, `skill-rules.ts`, spec §10):** `SkillCatalog` loads the platform skills once at boot (`loadSkillDir(ASSISTANT_SKILLS_DIR)`, `packages/ai-core/assistant-skills/<name>/SKILL.md`, ruling 1b-R3; a bad skill fails the start). Platform skills: `add-products`, `connect-channels`, `handle-orders`, `read-revenue`, `set-up-bot`. Owner, learned and shadow skills are `assistant_skills` rows. `SkillsService.catalog(owner)` = the platform skills, where the owner's **active** `shadow` row (name = the platform name, `shadow_of`) replaces the platform skill it copies, plus the owner's other active rows; the index is `- <name>: <description>` sorted by name, no provenance marker, and goes into the frozen prompt (thread start and compaction only). Tools: `skills_list` (name + description from the catalog); `load_skill({name})` resolves through the catalog (`unknown_skill`); for the review actor only it also resolves a `learned` skill in `pending_approval`, so a later review can refine a draft before the owner approves it (ruling 1c-R7; not counted as a use); it bumps a row's `use_count`/`last_used_at` and records the name in the run's `loadedSkills`; `skill_manage({action: create | patch | archive, name, description?, body?, reason?})` (toolset `skills`, not read-only), whose actor (`assistant` in the chat turn, `review` for the background review) and `loadedSkills` set come from the tool context. Chat: `create` → an `owner` skill, active at once (the description says only when the owner explicitly asks "lưu thành quy trình"); `patch` → an owner or learned skill loaded in this turn; `archive` → `not_allowed`. Review: `create` → a `learned` skill in `pending_approval`; `patch` → an unpinned learned skill loaded in this run (`patch_count` + 1); `archive` → unpinned learned skills only. Owner skills, pinned skills and shadows are never the review's (`not_allowed`, ruling 1c-R6, as Hermes protects them). Either actor: a platform skill or a shadow is `platform_skill_immutable`; a patch of a skill not loaded in the run is `load_first` (a skill created in the run counts as loaded); `missing_fields`, `unknown_skill`, `stale_skill` (optimistic `updated_at`). Every write: `lintSkill` (`invalid_skill:<problems>`; the description must be one line, since it is one line of the prompt's index — the contracts' request schemas refuse `\r`/`\n` too), a name taken by a platform skill or a non-archived row is `name_taken`, more than 50 active or pending owner + learned skills is `skill_limit` (shadows not counted), and one ledger row (`assistant_skill_events`, actor + before/after snapshots, the run id) in the same transaction. Owner routes (ledger actor `owner`): list (platform entries `ref = platform:<name>`, `provenance: platform`, `shadowed` = an active shadow replaces it; then every row with state and counters), read by `skillRef` (row id or `platform:<name>`), create (active; 400 `VALIDATION_FAILED` with `details.problems` when the lint fails, 409 `skill_name_taken`, `skill_limit`), patch (description/body/pinned; a content change is a ledger `patch` with `patch_count` + 1, a pin alone writes no ledger row), approve/reject (body `{expectedUpdatedAt}` = the skill's `updatedAt` as the owner saw it; a skill changed since, e.g. a review patched the draft, is 409 `skill_changed`; `pending_approval` → `active`/`archived`, else 409 `skill_not_pending`), archive (409 `skill_archived`), restore (`stale`/`archived` → `active`; 409 `skill_not_restorable`, `skill_limit`, `shadow_exists`), shadow (copies the platform body and toolsets; at most one non-archived shadow per platform skill, else 409 `shadow_exists`), DELETE (shadows only, else 409 `not_a_shadow`; the row is archived, not removed, so the ledger stays and the deletion can be undone; 204), events (newest first), undo (the entry's `before` snapshot comes back, or a created skill is archived; an `undo` row is appended and the entry gets `undone_at`; 409 `event_already_undone`, `event_not_undoable` for an `undo` entry, `stale_skill` when the skill no longer matches the entry's `after` snapshot; the snapshot it restores is linted again, 400 when it no longer passes). Another owner's skill or ledger entry is 404.

**Background review (`application/review-trigger.ts`, `review.service.ts`, `assistant-runner.ts`, spec §11, ruling 1c-R1):** after a turn that answered (never a failed or interrupted turn, a `schedule` thread, or with `review_enabled = false`), the chat turn adds 1 owner turn and the turn's tool rounds to the thread's counters; a turn in which the assistant itself wrote memory or a skill (an ok `memory` / `skill_manage` step) resets them instead. `planReview`: ≥ 8 owner turns → `review`/`memory` now; ≥ 10 tool rounds → `review`/`skills` now (both → `combined` now); else ≥ 3 owner turns → `combined` at now + 30 min. `enqueueJob` updates an existing queued job (its `run_after`, `review_scope`, and `created_at` = the last enqueue), so each turn pushes the idle review back; a review enqueued to run now resets both counters. The worker (`AssistantJobRunner`, `ASSISTANT_RUNNER`) claims up to 3 due jobs per 15 s tick with a 5-minute lease (`claimJobs`, `app_system`) and runs them side by side; a `curator` job goes to the curator (below), an unknown kind is failed (`unknown_kind`). `ReviewService.run` cancels the job (fenced on its `attempts`, so a stale attempt cannot cancel a later one) when review is off, the thread is gone or a schedule thread, the thread's `last_message_at` is after the job's `created_at`, or the owner is no longer an active owner (`resolveOwnerScope` on the thread's business when the owner is still a member of it, else any business of the account). The run: the thread's frozen system prompt, then `assistant-review@1` (`packages/ai-core/prompts`, ported from Hermes' background review) with the last 24 active messages as a digest (one line each; tool calls by name and ≤ 120 chars of arguments; tool results cut to 300 chars; every non-owner line — assistant text, summary, event, tool name, arguments and result — is flattened by `asData`: line breaks become ` ⏎ ` and role tags such as `[owner]` become `(owner)`, so quoted customer text cannot pass for an owner line, and the prompt says only `[owner]` lines are signals), the owner's memory as it is now (read from the repository, not the frozen prompt's snapshot) and the scope's focus; tools `memory` (origin `review`), `skills_list`, `load_skill`, `skill_manage` (actor `review`, its own `loadedSkills`), `session_search` and `suggest({kind, dedup_key, title, payload})` (≤ 5 pending per owner `suggestion_limit`, a known key `already_suggested`, payload ≤ 2 000 chars, safety-scanned); tier `pro`, the thread's `promptCacheKey` plus `:review` (its tool list differs from the chat's, so it keeps its own cache bucket), 8 rounds, 120 s, and it stops before the next model call once its input tokens (cached included) reach 200 000 (outcome `token_budget`). Every memory, skill or suggestion write first re-reads the job: still `running`, same `attempts`, lease ≥ 30 s left; otherwise the write answers `lease_lost`, the run stops and the job is left to its new holder. The run is recorded as `assistant_runs.kind = 'review'` (prompt version `assistant-review@1`) with its steps; it never writes to the transcript. Done: the counters are reset, `last_review_at` set, the job `done`. A failure: logged by job id and error class; `attempts < 2` → `retryJob` (queued again in 10 min, `error_code = review_failed`; failed instead when another job of the thread is queued), else `failed`.

**Learning feed (`application/learning-feed.ts`, ruling 1c-R2):** `GET /assistant/learning?days=N` = the owner's skill ledger rows by `review` and `curator` (`kind: skill`, with action, name, description, the state after, `undone`, `skillEventId` → `POST /assistant/skill-events/{id}/undo`) plus memory entries with origin `review` saved or replaced in the window (`kind: memory`, `store` + `entryId` and `previousText` → `POST /assistant/memory/{store}/entries/{entryId}/undo`: an entry the review rewrote gets its previous text and origin back, an entry it added is forgotten), newest first, at most 20. Memory entries carry `origin` (`assistant` | `review` | `owner`; entries from before 1c are `assistant` or `owner`) and, once replaced, `updatedAt`; an entry the review rewrote also keeps `previousText`/`previousOrigin` (the text before its first review rewrite), dropped by any later non-review write.

**Curator (`application/curator.service.ts`, spec §10, rulings 1c-R4, 1c-R5):** deterministic, no LLM call. The runner's tick looks at most every 10 minutes (per worker process) for owners with an `active` or `stale` learned skill whose `assistant_settings.curator_ran_at` is older than a day (`ownersWithLearnedSkills`, `app_system`), enqueues one `curator` job each (`run_after` = now; a user who is no longer an owner of the account is skipped, and its job, if one runs, changes nothing) and sets `curator_ran_at` = now at once, so an owner gets at most one run a day. The job, for each learned skill (`listLearnedSkillsForCurator`): pinned skills and skills younger than 30 days are skipped; idle = since `last_used_at`, or `created_at` when never used; `active` idle > 30 days → `stale` (hidden from the catalog), unless the owner touched it (`updated_at`: approved, restored, edited) in the last 30 days; `stale` idle > 90 days → `archived`. One step per run (an active skill goes stale before it can be archived). Each change is an optimistic update with a ledger entry, actor `curator`, action `archive` (the ledger has no `stale` action; `after.state` says `stale` or `archived`), so it shows in the learning feed and can be undone; a skill changed meanwhile is skipped. A failure is logged by job id and error class and the job is failed (`curator_failed`), no retry: the next day's run covers it. Schedule references (spec §10) do not exist yet.

**Settings and toolsets (`application/settings.service.ts`, `toolsets.ts`, spec §6):** toolsets `core` (`session_search`), `ui` (`ui_navigate`, `ui_spotlight`, `ui_fill_form`), `memory` (`memory`), `skills` (`skills_list`, `load_skill`, `skill_manage`) and `routes` (`tool_search`, `tool_describe`, `tool_call`); every turn tool is in exactly one. `GET /assistant/settings` → `{reviewEnabled, disabledToolsets, toolsets: [{id, labelKey (web i18n key toolsets.<id>), toolCount, uses30d, locked}]}`; `uses30d` counts the tool steps of the owner's **chat** runs created in the last 30 days (`countToolUses`), summed per toolset (the toggles only change chat turns). `PATCH /assistant/settings` (`reviewEnabled`, `disabledToolsets`; partial, not empty): `core` and `ui` cannot be disabled (400 from the request schema, and `AssistantSettingsInvalidError` in the service); the stored list is sorted and unique. The chat turn reads the settings once per turn (the defaults when the read fails): the disabled toolsets' tools are removed from both the definitions sent to the model and the runnable tools, and the prompt-cache key gets the suffix `:off=<sorted ids>` (none when all are on), so a smaller tool list never shares a cache entry with the full one. The background review keeps its own tool list (it is switched by `reviewEnabled`).

**Feedback:** `POST /assistant/messages/{messageId}/feedback {value: 1 | -1 | 0}` → 204; 0 clears it. Only an assistant answer of the owner's own thread (`setFeedback`); any other message, a malformed id or another owner's message is 404. Message DTOs carry `feedback` (1, -1 or null).

**Suggestions (`application/suggestions.service.ts`, ruling 1c-R3):** cards saved by the review's `suggest` tool. `GET /assistant/suggestions` = pending ones, newest first. `POST …/accept`: `skill` → the payload `{name, description, body}` is parsed as `CreateAssistantSkillRequest` and saved as a `learned` skill in `pending_approval` through `SkillsService.draftFromSuggestion` (lint, name, limit, ledger actor `review`), so the owner approves its body on the normal pending card; a refused skill answers 400/409 and the card stays pending; `setup` → accepted, and the payload's `path` is returned when it is a safe in-app path (`/app…`, no `//`, `..` or `\`), else null; `schedule` → accepted only, until schedules exist. Answers `{suggestion, skill, path}`. `POST …/dismiss` → the dismissed card. A card that is not pending is 409 `suggestion_not_pending`; another owner's or a malformed id is 404. A dismissal is permanent: the `dedup_key` stays taken in every status, so the review's `suggest` answers `already_suggested`.

**Web client:** `apps/web/src/features/assistant` (launcher in `routes/app.tsx`, owners only; panel and `assistant` i18n namespace lazy-loaded; steps polled from `GET /assistant/runs/{runId}` every second while a turn runs; `ui_navigate` re-checked client-side by `safeAppPath`; an answer that arrives after the owner switched business is not applied). 1b adds proposal cards (an action line from `routeKey`: verb + route path, DELETE/PUT styled destructive; preview open by default for PATCH/PUT/DELETE with `before` next to the body; approve/reject; the busy state is keyed by the proposal id, so it survives switching panel views; an approval refetches the business's `['ws', businessId]` queries), the memory view, and form filling through `apps/web/src/lib/assistant-context.ts` (`useAssistantForm`; numbers sent as text are read Vietnamese style: `150.000` is 150 000, `12.5` and `12,5` are 12.5). 1c adds (`api/assistant-skills.ts`, `api/assistant-settings.ts`): the **Kỹ năng** view (sections pending / the owner's / learned / platform / archived; a pending learned skill is a one-tap Duyệt/Bỏ card with its body on demand, sending the `updatedAt` shown (a 409 `skill_changed` refetches the skill and says so in a toast); each skill opens an editor (description + body, Lưu sends only what changed) with its ledger and "Hoàn tác" per entry; a platform skill is read-only with "Tinh chỉnh" (creates a shadow and opens it); a shadow has "Khôi phục bản gốc" (DELETE); archived and stale skills can be restored; archived shadows are not listed), the **learning notice** under the panel header (`GET /assistant/learning`: at most 3 lines, undone skill items hidden, each with "Hoàn tác" (skill-event undo, or the memory undo route; a rewritten entry reads "old → new") and "Xem" for a pending skill; closing it remembers the newest shown item in `localStorage`, per browser), **suggestion cards** above the composer (Đồng ý / Bỏ qua; a `skill` card shows the skill's name, description and its body on demand before accept; an accepted `setup` card navigates to its `path` only through `safeAppPath`), **👍/👎** under every answer (optimistic over every cached message list, pressing the chosen one again sends 0, a failure refetches), and the **Cài đặt trợ lý** view (review switch, toolsets with their 30-day use, `core`/`ui` locked, a link to the memory view). No SSE streaming yet (spec §18, §19, §20).

**Invariants:**

- Owner-only: every facade call starts with `resolveOwnerScope` (`application/owner-access.ts`); the caller must be an active `owner` of the account that owns the current business, else 403 `FORBIDDEN` (billing members and staff are refused). The scope carries `businessIds`: the account's businesses the owner is an active member of (sorted, always including the current one).
- Account scope AND owner: every repository method runs in one `withAccount` transaction and filters by `account_id` and `owner_user_id`; a thread or run of another owner (even of the same account) is 404. Methods taking a `threadId`/`runId` verify ownership in the same transaction first, because the `thread_id` foreign keys alone do not carry the owner.
- Tool rows (`role = 'tool'`), assistant rows that only requested tools, and compaction summaries (`is_summary`) never leave the backend; message DTOs carry `user`, `assistant`, `event` only.
- A thread's system prompt (`assistant@2` for new threads; older threads keep `assistant@1`) is frozen at creation (owner name, the account's businesses as `- <name> (<industry>) — id <uuid>`, the skills index, the memory snapshot read at creation (`<store> [<pct>% — <used>/<limit>]` headers, then `- <text>`; entries that fail the safety scan are skipped), today's date in Asia/Ho_Chi_Minh), so it stays byte-stable for prompt caching. Memory written during a thread joins it only in a new thread or after compaction (1b-R6).
- No business data is copied: the assistant reads other modules through their facades and declared routes at answer time; only the conversation, run traces, memory and proposals are kept. The one exception is a proposal's own request, `before` snapshot and ≤ 1 000-char result preview (see Proposals).
- No monthly allowance or quota yet (1a, 1b): tokens are recorded on `assistant_runs`; the cap arrives with billing in a later slice (spec §18).
- One running run per owner (younger than 3 min); a run id is the client `turnId`, so a retried turn is a duplicate, not a second run.
- Repository (1b storage): `getMemory` / `saveMemoryStore` (upsert of one store's entries); `createProposal` / `listProposals` / `getProposal`, `transitionProposal(from[], to)` is one conditional UPDATE (null when no row changed: the atomic approve guard), `expireProposals(now)`; `applyCompaction` in one transaction (middle → `active=false, compacted=true`; pruned tool rows → `PRUNED_TOOL_TEXT`; summary row `is_summary`, `seq = max+1`, `sort_seq = summarySortSeq(summarised)` = lowest sort_seq of the summarised ordinary rows − 0.5, a folded summary not counted, so it stays between head and tail on every compaction; thread `system_prompt`, `compacted_at`, last two `compaction_saved_pcts`, `cache_root_id` set to the thread id when null; a stale plan throws and changes nothing), `markCompactionFailed`; `getLastChatRun` (the thread's newest `done` chat run) and `recordRun` (a finished run of any kind, e.g. `compaction`). `listMessages({ activeOnly })` orders by `sort_seq`.

**Do not:** read other modules' tables; use `withTenant` for assistant tables; put HTTP/Drizzle types in `domain/`; call LLMs outside `ai-core`.
