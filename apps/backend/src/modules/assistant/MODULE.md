# assistant

**Purpose:** the owner assistant "Thỏ Rapiz" (ADR-022, T-170): an account owner's private chat threads, the runs that answer them and their steps. Owner-only and account-scoped, not business-scoped.

**Owned tables:** `assistant_threads`, `assistant_messages`, `assistant_runs`, `assistant_run_steps` (migration 0055), `assistant_memory`, `assistant_proposals` and the compaction columns (`assistant_threads.cache_root_id`, `compacted_at`, `compaction_failed_at`, `compaction_saved_pcts`; `assistant_messages.sort_seq`) (migration 0056); schema in `packages/db/src/schema/assistant.ts`. Every row carries `account_id`; RLS reads `app.account_id`, set by `withAccount`. `assistant_messages.search` (generated tsvector, GIN + trigram indexes) exists only in SQL and is queried with `sql`.

**Public API (`api/`):**

- `ASSISTANT_FACADE` → `AssistantFacade.listThreads | createThread | updateThread | listMessages | sendMessage | getRun | getMemory | deleteMemoryEntry | listProposals | approveProposal | rejectProposal` (actor = user + current business; `sendMessage` and `approveProposal` also take the caller's `Authorization` header, held in memory only; `sendMessage`'s actor may carry a lazy `displayName`, read only when the turn compacts the thread). No other module consumes it yet.
- HTTP (`assistantRoutes`, all `@WorkspaceScoped()`, all `assistant: never`): `GET/POST /assistant/threads`, `PATCH /assistant/threads/{threadId}`, `GET/POST /assistant/threads/{threadId}/messages`, `GET /assistant/runs/{runId}`, `GET /assistant/memory`, `DELETE /assistant/memory/{store}/entries/{entryId}`, `GET /assistant/threads/{threadId}/proposals`, `POST /assistant/proposals/{proposalId}/approve|reject`. `POST …/messages` runs one chat turn (below) and answers 200 with the turn's visible messages and its run; 409 `CONFLICT` (`details.reason = assistant_busy`) while another run of the owner is running, or for a retried `turnId` whose run is still running, or (`turn_id_taken`) when the `turnId` is another owner's run or a run of another thread; 503 `AI_UNAVAILABLE` when no model serves the `pro` tier. `GET /assistant/memory` lists owner_profile, notes, then one `business:<id>` store per business of the account the owner is a member of (by id), empty ones included, each with `label` (English key, or the business name), `limit` and `used`; `DELETE …/entries/{entryId}` answers 200 with the remaining memory, 404 for an unknown store or entry.
- Events: none.

**Depends on:** `account` (`listForUser`: owner role), `workspace` (`accountOf`, `listMemberships` for the prompt's business list), `ai` (`AI_LLM_GATEWAY` for chat turns, `isAiNotConfiguredError` to answer 503). Other modules' data is reached only through their declared HTTP routes (`ROUTE_INVOKER` → `infrastructure/http/fastify-route-invoker.ts`, Nest `HttpAdapterHost` + Fastify `inject` on `/api/v1`), never their internals.

**Chat turn (`application/chat-turn.service.ts`):** `startRun` (id = `turnId`, tier `pro`, the thread's prompt version) → store the owner's text (raw, with its `pageContext`) → `CompactionService.maybeCompact` with the thread's last finished chat run (any error is logged and the turn goes on with the full history) → history = all active messages by `sort_seq`, safety-capped at the last 200 and starting at a user, event or summary message (a tool call never loses its results) (`event` rows as `[event] …` user messages); only the last user message is sent as `buildTurnMessage` (`<page_context>` JSON, `<current_time>` HH:mm in Asia/Ho_Chi_Minh, then the text) → `runAgentLoop` on `AI_LLM_GATEWAY` with the core, memory, skill and route tools (definitions sorted by name), at most 25 rounds and 90 s (less the time a compaction took, at least 30 s), 60 s per model call, an owner-facing wrap-up notice at 80 %, `promptCacheKey = asst:<owner>:<cache_root_id ?? thread>` (stable: the root is the thread id) → store the tool exchange (hidden) and the answer with the turn's `uiActions` (at most the last navigate, the last fill_form and the last spotlight, in that order; none when the turn did not answer) → `finishRun` (usage, rounds = model calls, latency, provider/model). Steps are written as they happen (kind, tool name, ok, ms; never arguments or results). No answer text, or an outcome other than `done`, gives the fallback reply; a model error gives the fallback reply too, with the run `failed` (`guardrail = model_error`). An untitled thread takes the first 60 characters of its first message as its title. Logs carry the run id, tool name and error class only.

**Core tools (`application/core-tools.ts`, results ≤ 8 000 chars):** `session_search({query, limit≤10=3})` over the owner's earlier user/assistant messages; `ui_navigate({to})` only for `/app` or `/app/…` by the same rule as the web app's `safeAppPath` (decoded until stable, no `%`, query, hash, backslash, `//`, control character or dot segment; ruling R6), else `invalid_path`; `ui_spotlight({target, hint})` only for a target listed in the page context, else `unknown_target`. `ui_fill_form({formId, values})` drafts values into a form the page context lists: `formId` must be one of `page.forms[].id` (`unknown_form`), every key a declared field (`unknown_field:<name>`), a `select` value one of its options (`invalid_option:<name>`), strings ≤ 4 000 chars (`too_long:<name>`), at least one value (`no_values`); it answers "filled as a draft; the owner reviews and saves it themselves" and never submits. The UI tools add to the answer's `uiActions`; none of them changes data.

**Memory tool (`application/memory-tools.ts`):** `memory({action: add | replace | remove, store, text≤1000, match≤200})`. Stores (`domain/memory-store.ts`): `owner_profile` 1 400, `notes` 2 200, `business:<id>` 1 000 chars (used = sum of entry lengths); a business store must name one of `scope.businessIds`, else `unknown_store`. `add` needs `text`, `replace` needs `match` and `text`, `remove` needs `match` (`missing_text` / `missing_match`); `match` must be a substring of exactly one entry (`match_not_found` / `match_not_unique`); exact duplicates are `duplicate`; new text goes through `scanUntrustedText` (`unsafe:<issues>`) and is folded to one line; a write past the limit answers `store_full` with the entries and "consolidate: replace or remove entries first". After 3 failed calls in a turn every further call answers `stop_retrying`. Success: `{ok, message, used, limit}`. Memory text is never logged.

**Route tools (`application/route-catalog.ts`, `route-tools.ts`, spec §6):** the catalog is built once from `allRoutes`: workspace-scoped routes whose `assistant.use` is `read` (a GET, or a POST flagged `queryPost`, ruling 1b-R7) or `write` (never a GET); a missing field is unusable and `/assistant`, `/auth` routes are excluded whatever they say. Entries are keyed `METHOD /path`. `tool_search({query})` → the top 8 `{key, use, summary, when}` by word overlap (unaccented, lowercased, plural `s` folded) with key, summary and `when`, boosted when the route's first path segment is the page's `/app/<section>`. `tool_describe({key})` → `{key, use, pathParams, query, body}` (JSON schema, `io: input`, ≤ 8 000 chars) or `unknown_key`. `tool_call({key, businessId?, params?, query?, body?, summary?})`: `businessId` defaults to the current business and must be in `scope.businessIds` (`unknown_business`); every path param must match `^[A-Za-z0-9_-]{1,64}$` (`bad_params`); query (as strings) and body are checked with the route's Zod schemas (`invalid_input` + first 5 issues). A **read** runs through `ROUTE_INVOKER` with the owner's own bearer token, `X-Workspace-Id` = the business and `X-Actor: assistant`, so the real auth guard, capabilities and RLS apply; the result `{status, body}` is ≤ 8 000 chars (`…[truncated]`) and read results share a 40 000-char budget per turn (`turn_budget_exhausted`); HTTP ≥ 400 → `http_<status>` (403 adds "Tài khoản của anh/chị không có quyền này"). A **write** never runs: it needs `summary` (`summary_required`) and becomes a pending proposal (expires in 24 h) whose `preview` is `{body, query}` plus, for PATCH/PUT/DELETE with a GET on the same path, `before` (the current state, read with the owner's token); the result is `{status: 'awaiting_owner_approval', proposalId}`. `tool_call` is not read-only for the loop, so calls run in order. The bearer token lives in the turn's memory only: never stored, logged or put in a step.

**Proposals (`application/proposals.service.ts`):** list = expire stale pending proposals, then the thread's proposals oldest first. Approve/reject: the proposal must be the owner's and its business still in `scope.businessIds` (else 404); stale ones expire first. Approve = `transitionProposal(pending → executing)` (the atomic guard; null → 409 `proposal_not_pending`, or `proposal_expired` when it expired; one that expired since is moved to `expired` → 409 `proposal_expired`), then the stored request runs with the **approver's** token and `Idempotency-Key: asst:<id>`; 2xx → `done` with `resultPreview` (≤ 1 000 chars), else `failed` with `http_<status>` (`invoke_failed` when the call threw). Reject = pending → `rejected`. Each decision appends an `event` message (`Đã áp dụng: …`, `Không áp dụng được: … (<code>)`, `Anh/chị đã bỏ: …`), so the next turn sees it.

**Compaction (`application/compaction.service.ts`, spec §9):** skipped during the 10-minute cooldown after a failure (`compaction_failed_at`) and when the last two `compaction_saved_pcts` are both < 10. Due when `shouldCompact` says so: the last finished chat run's `(input_tokens + cached_tokens) / rounds` (runs store usage summed over their model calls, so the per-call average stands in for the last call) ≥ 75 % of (`ASSISTANT_CONTEXT_TOKENS` 128 000 − `ASSISTANT_MAX_OUTPUT_TOKENS` 16 000), or more than 80 active messages. Then `planCompaction` (null → nothing) and one summariser call on tier `basic` (`buildCompactionPrompt`, the previous summary updated, 30 s cap, same `promptCacheKey`), recorded as an `assistant_runs` row of kind `compaction`. The summary row (role `user`, `is_summary`) is `COMPACTION_SUMMARY_PREFIX` + the text + the thread's pending proposals (`- <summary> (id: <id>)`); the thread's system prompt is rebuilt (`ThreadPromptService`: businesses, skills index and a fresh memory snapshot, the thread's own prompt version); `savedPct` = 1 − chars after / chars before over the active messages; `applyCompaction`. Any failure (model error, empty summary, stale plan) calls `markCompactionFailed` and keeps the history. The summary is for the model only: `isVisibleMessage` hides it and search skips it.

**Skills (`application/skill-tools.ts`):** `SkillCatalog` loads the platform skills once at boot (`loadSkillDir(ASSISTANT_SKILLS_DIR)`, `packages/ai-core/assistant-skills/<name>/SKILL.md`, ruling 1b-R3; a bad skill fails the start). `skills_list` returns name + description; `load_skill({name})` returns the body or `unknown_skill`. Platform skills: `add-products`, `connect-channels`, `handle-orders`, `read-revenue`, `set-up-bot`.

**Web client:** `apps/web/src/features/assistant` (launcher in `routes/app.tsx`, owners only; panel and `assistant` i18n namespace lazy-loaded; steps polled from `GET /assistant/runs/{runId}` every second while a turn runs; `ui_navigate` re-checked client-side by `safeAppPath`; an answer that arrives after the owner switched business is not applied). Not in 1a: proposals and any write tool, `ui_fill_form`, route-derived tools, memory, skills, compaction, SSE streaming (spec §18); memory, platform skills, route tools, proposals, compaction and `ui_fill_form` arrive in 1b (the web's proposal cards and form filling in a later task).

**Invariants:**

- Owner-only: every facade call starts with `resolveOwnerScope` (`application/owner-access.ts`); the caller must be an active `owner` of the account that owns the current business, else 403 `FORBIDDEN` (billing members and staff are refused). The scope carries `businessIds`: the account's businesses the owner is an active member of (sorted, always including the current one).
- Account scope AND owner: every repository method runs in one `withAccount` transaction and filters by `account_id` and `owner_user_id`; a thread or run of another owner (even of the same account) is 404. Methods taking a `threadId`/`runId` verify ownership in the same transaction first, because the `thread_id` foreign keys alone do not carry the owner.
- Tool rows (`role = 'tool'`), assistant rows that only requested tools, and compaction summaries (`is_summary`) never leave the backend; message DTOs carry `user`, `assistant`, `event` only.
- A thread's system prompt (`assistant@2` for new threads; older threads keep `assistant@1`) is frozen at creation (owner name, the account's businesses as `- <name> (<industry>)`, the skills index, the memory snapshot read at creation (`<store> [<pct>% — <used>/<limit>]` headers, then `- <text>`; entries that fail the safety scan are skipped), today's date in Asia/Ho_Chi_Minh), so it stays byte-stable for prompt caching. Memory written during a thread joins it only in a new thread or after compaction (1b-R6).
- No business data is stored: the assistant reads other modules through their facades at answer time; only the conversation and run traces are kept.
- No monthly allowance or quota in 1a: tokens are recorded on `assistant_runs`; the cap arrives with billing in a later slice (spec §18).
- One running run per owner (younger than 3 min); a run id is the client `turnId`, so a retried turn is a duplicate, not a second run.
- Repository (1b storage): `getMemory` / `saveMemoryStore` (upsert of one store's entries); `createProposal` / `listProposals` / `getProposal`, `transitionProposal(from[], to)` is one conditional UPDATE (null when no row changed: the atomic approve guard), `expireProposals(now)`; `applyCompaction` in one transaction (middle → `active=false, compacted=true`; pruned tool rows → `PRUNED_TOOL_TEXT`; summary row `is_summary`, `seq = max+1`, `sort_seq = summarySortSeq(summarised)` = lowest sort_seq of the summarised ordinary rows − 0.5, a folded summary not counted, so it stays between head and tail on every compaction; thread `system_prompt`, `compacted_at`, last two `compaction_saved_pcts`, `cache_root_id` set to the thread id when null; a stale plan throws and changes nothing), `markCompactionFailed`; `getLastChatRun` (the thread's newest `done` chat run) and `recordRun` (a finished run of any kind, e.g. `compaction`). `listMessages({ activeOnly })` orders by `sort_seq`.

**Do not:** read other modules' tables; use `withTenant` for assistant tables; put HTTP/Drizzle types in `domain/`; call LLMs outside `ai-core`.

**Test:** `pnpm --filter @agent-sales/backend test -- assistant`; integration: `test/assistant.integration.spec.ts`.
