# commerce

**Purpose:** the shop's catalog and orders — warehouses, products with variants, inventory with a movement log, orders with items, status flow and history, order settings, and the sales overview (docs/02 ORD-01..05, ORD-11).

**Lodging (T-155):** hotel workspaces add whole-property metadata on `products` and commerce-owned `stay_requests` (migration 0035). See [lodging operations](../../../../../docs/lodging.md) and ADR-013 for date quotes, explicit staff confirmation, overlap exclusion, idempotency, permissions and API pagination. Lodging never enters retail stock/order lines.

**Owned tables:** `warehouses`, `products`, `product_variants`, `inventory`, `inventory_movements`, `order_counters`, `orders`, `order_items`, `order_status_history`, `order_settings`, `bot_products`, `stay_requests` (tenant, forced RLS — migrations 0004, 0005, 0014, 0029 and 0035; schema in `packages/db/src/schema/commerce.ts`).

**Public API (`api/`):** `COMMERCE_FACADE` → `getOrder(workspaceId, orderId)`; `CATALOG_FACADE` → `searchBotCatalog(workspaceId, bot, {query?, maxPriceVnd?, inStockOnly?, limit})` (the bot's `search_products` tool, ADR-014 — ranked by pg_trgm `word_similarity` over the folded `search_text` and category, floor 0.3, name/id tie-break, max 300 rows — `getBotProductsByIds` and `countBotCatalog`; read-only, active and `visibleToBot` only, with `imageUrls`; `bot` is `{ botId, catalogMode }` and `selected` restricts to the bot's selection, T-080). HTTP (workspace-scoped): `/warehouses`, `/products`, `/products/{id}/stock`, `POST /products/images` (see below), `/product-variants`, `/bots/{botId}/products` (GET; PUT replaces the selection, `catalog.manage`; selecting a product of another workspace, or for a bot of another workspace, is 404 — the composite keys refuse the row. Commerce does not read `bots`, so an empty PUT or a GET for another workspace's bot sees no rows: 200 with nothing changed or `[]`, never another workspace's data. Saves of one bot's selection are serialized by an advisory lock; creating a product with `botId` adds one row), `/orders`, `/orders/overview`, `/orders/{id}`, `/orders/{id}/status`, `/order-settings`. Contracts: `packages/contracts/src/commerce/`.

**Events consumed:** none. Uses the `identity` facade (name snapshots) and the `workspace` facade (time zone).

**Invariants:**

- Money is integer VND; amounts follow docs/05 §6 exactly (`computeAmounts` in `packages/shared`, shared with the order form; unit-tested). `gross` ("Tổng số tiền") is before the discount, `total` ("Tiền cần thu") after it.
- Lines can be edited (`PATCH /orders/{id}` with `items`) only while the order holds its goods (`stock_state = reserved`); otherwise 409 and nothing changes. The reservation moves by the per-variant difference (`reservationChanges`); a variant already on the order keeps its snapshot (names, cost, price unless a new price is sent), a new variant must be on sale and takes the catalog price.
- Source field policies (`order-rules.ts`): saving an order checks its source's `create` fields; creating it in, or moving it into, a fulfilment status also checks the `confirm` fields; editing the people of an order re-checks the stage it is in. Settings saves carry `version` (stale → 409).
- Stock follows the order (`domain/order-stock.ts`): a live order holds its goods (`reserved`), the first shipped status (delivering, delivered, delivery failed, returning) takes them out, `cancelled` gives held goods back, goods already out can only come back as `returned`. Every change writes `inventory_movements`.
- Concurrency: edits and status changes lock the order row (`SELECT … FOR UPDATE`), stock-takes lock the inventory row; held stock is never clamped, so a negative hold fails the CHECK constraint instead of hiding a bug.
- Creating an order is idempotent per `clientRequestId` (one per form draft): a retry or double submit returns the first order.
- Overselling is allowed on purpose (pre-orders, shops that do not track stock): orders may take more than `on_hand − reserved`; the order form warns per line. Revisit if a shop needs a hard limit (owner decision).
- Products carry up to 5 `imageUrls` (https only, 2000 characters each; migration 0014, `products.image_urls`); they are returned by the bot catalog methods (`searchBotCatalog`, `getBotProductsByIds`) so the bot can send them (the AI module builds the allowlist, never the URLs into the prompt). The AI module reads the catalog only on demand through the bot's tools (`searchBotCatalog`, `getBotProductsByIds`, `countBotCatalog`); the earlier server-side guessing (`getBotProducts`, `listBotCatalog`, `botProductSearches`) was removed.
- Search treats `%`, `_` and `\` literally.
- Order codes are `DH` + 6 digits, incrementing per workspace (`order_counters`, row-locked by the upsert).
- Optional statuses (awaiting print, printed) can only be used when switched on in order settings; statuses listed as "require note" reject a change without a note.
- Variants are archived, never deleted (past orders reference them); SKUs and product codes are unique per workspace, case-insensitive.
- Overview figures are per local day in the workspace time zone and use the same rows as the order list (sales = all but cancelled; revenue/profit/closed = `CLOSED_ORDER_STATUSES`).
- Names of who created/changed an order are snapshotted (the `users` table is global).

**Do not:** read other modules' tables; compute money with floats; update `inventory` without a movement; delete orders or variants.

**No database:** routes answer 503 `UNAVAILABLE` (the SQL search and aggregates have no faithful in-memory fake). Test with `test/commerce.integration.spec.ts`.

**Test:** `pnpm --filter @agent-sales/backend test -- commerce` · integration: `test/commerce.integration.spec.ts`

**Product pictures (`POST /products/images`, `catalog.manage`):** body `{ mimeType: image/jpeg|png|webp, base64 }`; the bytes are verified by magic bytes (max 1 MiB decoded; request body limit 2 MiB, raised per route via `@RouteConfig({ bodyLimit })` + the `onRoute` hook in `bootstrap.ts`), stored by `ProductImageService` in Rapiz's own S3-compatible storage under `products/<workspaceId>/<uuidv7>.<jpg|png|webp>` and answered `201 { url }` (`${S3_PUBLIC_URL}/<key>`). Never falls back to local disk. Errors: 400 `VALIDATION_FAILED` with `details.reason = INVALID_IMAGE`; 503 `UNAVAILABLE` with `details.reason = MEDIA_STORAGE_UNAVAILABLE` (storage not configured or down). Adapter: `common/storage` (`S3PublicObjectStorage`, shared with knowledge).

**Only uploaded pictures are accepted.** On product create/update, every `imageUrls[i]` and accommodation `gallery[i].url` must be a Rapiz-stored file of the same workspace (`${S3_PUBLIC_URL}/products/<workspaceId>/<file>.<jpg|png|webp>`, checked in `CatalogService` with `domain/own-image.ts`). Anything else (external link, another workspace's file, traversal, storage not configured) is 400 `VALIDATION_FAILED` with `details = { reason: 'IMAGE_NOT_UPLOADED', field: 'imageUrls[i]' | 'gallery[i].url' }`. An update that keeps a value already stored on the product is not exempt: legacy external URLs must be gone, so run the import CLI first in every environment.

**Import CLI for linked pictures.** `pnpm --filter @agent-sales/backend product-images:import [--dry-run] [--workspace <id>]` (needs `DATABASE_SYSTEM_URL` and the `S3_*` env) downloads every picture and gallery photo that is not yet under `${S3_PUBLIC_URL}/products/<its workspace>/` (15 s timeout, at most 3 redirects, 10 MiB, `Accept: image/jpeg,image/png,image/webp`, magic-byte check), stores it as `products/<workspaceId>/<uuidv7>.<ext>` and rewrites the URL in place, one transaction per product. Idempotent (failed pictures keep their old URL and are retried next run); one upload per source URL per workspace per run; prints per-workspace counts (found, imported, already stored, failed by reason) and exits 1 if anything failed. Code: `domain/image-import.ts` (pure) and `infrastructure/image-import/`.
