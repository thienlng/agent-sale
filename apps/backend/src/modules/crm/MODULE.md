# crm

**Purpose:** the shop's customers — profiles with notes and an audit history, customer sources and pipeline statuses, Sales/CSKH ownership, tag definitions with attribute schemas and their assignments, typed filters and saved views (docs/02 CRM-01..CRM-10; GitHub epic #25, issues #26–#29).

**Owned tables:** `contacts`, `contact_notes`, `contact_history`, `crm_sources`, `crm_statuses`, `crm_tags`, `crm_tag_assignments`, `saved_views`, `crm_assignment_policies` (tenant, forced RLS — migrations 0006, 0014, 0051 for the PMS link columns; schema in `packages/db/src/schema/crm.ts`).

**Public API (`api/`):**

- `CRM_FACADE` → `getContact(workspaceId, contactId)`, `ownedContactCounts(workspaceId, userId)` and `reassignContacts(workspaceId, from, to | null, actor)` (used by `team` when a member is removed; history entries are written per customer), and for the inbox: `conversationTags(ws, ids)` (tag chips for list rows), `conversationIdsByTags(ws, { any, all, exclude, untagged })` (id sets the inbox applies to its own query), `upsertLeadByPhone` (lead capture from the website and from phone numbers in Facebook/Instagram messages, below), `recordContactBot(ws, contactId, botId)` (T-088: idempotent, NOT_FOUND for a customer of another business), `listConversationTags` and `assignConversationTag` (the conversation module checks the conversation exists and exposes `/conversations/{id}/tags`).
- `CONTACT_SYNC_FACADE` (`api/contact-sync.facade.ts`, used by `integration`; ADR-017): `upsertExternalContact`, `unlinkExternalContacts`, `claimContactsForPush`, `pushableContact`, `markContactPushed`, `markContactPushFailed`, `releasePendingContactPushes`, `releaseFailedContactPushes`, `staleContactPushes`, `releaseExternalSource`, `linkedContactCount`, `externalIdOf` (rules under "PMS link" below). `ContactDto.external` is `{ source: 'kiotviet', id } | null`.
- HTTP (workspace-scoped): `/contacts`, `/contacts/query`, `/contacts/{id}` (+ `/notes`, `/history`, `/tags`), `/tag-assignments/{id}` (+ `/remove`), `/crm/sources`, `/crm/statuses` (+ `/order`), `/crm/tags`, `/crm/assignees`, `/saved-views`. Contracts: `packages/contracts/src/crm/`.
- Events (outbox, same transaction as the change): `crm.contact.created.v1`, `crm.contact.updated.v1`, `crm.contact.status_changed.v1`, `crm.contact.assigned.v1`, `crm.tag.assigned.v1`, `crm.tag.removed.v1`. Statistics (analytics module) rely on them: `crm.contact.created.v1` carries `origin` and `phoneCaptured`, `crm.contact.updated.v1` carries `phoneCaptured`, and every owner a customer starts with is a `crm.contact.assigned.v1` (not only auto-assigned ones).

**Events consumed:** none yet. Uses the `identity` facade (actor names) and the `workspace` facade (members for assignment, time zone for date filters).

**Invariants:**

- A contact has at least a name, a usable phone or an email. Phones are stored as typed plus E.164 (`normalizeAnyPhone`); an unusable phone is rejected, not stored.
- Edits carry `expectedVersion`; a stale edit answers 409 and writes nothing. Only sent fields change (`null`/"" clears). "Provided at" timestamps are set when a phone/address first appears and are never touched by other edits. The first source is kept once set.
- Every change appends `contact_history` (field → {from, to}) in the same transaction; status and assignment changes get their own entries and events. Notes are separate from the 500-character profile note; editing a note keeps the old body in the history. Notes never message the customer.
- Sources, statuses and tags have stable ids and are archived, never deleted: archived ones stay on existing customers and in history but cannot be newly chosen. Defaults (7 sources, 8 statuses, 3 system tags) are seeded on first use by `key`. Customer settings (`/app/crm-settings`) is the one place that manages them; CRM, the inbox and statistics read the same ids (T-089). Active tags have distinct names (partial unique index); active sources and statuses too, checked by the service because older workspaces may already hold duplicates, which stay valid until renamed or archived. A clash answers 409 `CONFLICT` with `details.name`. Customer status is independent of the conversation's open/resolved state and of the bot switch.
- A customer's status never changes orders (orders have their own status; nothing in this module reads or writes them).
- Sales and CSKH are separate fields; both must be active workspace members when assigned.
- Classification and attribute tags are active at most once per customer (partial unique index): a retried add returns the existing assignment (200) and a retried remove is a no-op, so neither writes a second event. Work tags may repeat. Attribute values are validated on the server against the tag's fields; fields keep key and type forever and options are archived, never removed, so old values stay readable. Assignments record the schema version they were filled with. Contact and conversation scopes are distinct (`scope`). Conversation tags (inbox v2) use the same library and table with `scope = 'conversation'`; they write no customer history and publish no event, `activeCount` counts customers only, archived tags are hidden from chips and from the `untagged` filter, and removal goes through the shared `/tag-assignments/{id}/remove` route (editing values stays customer-only).
- One SQL compiler (`contact-filter.sql.ts`) builds the WHERE for rows and the total. Null rule: a customer without a value matches `is_empty` and the negative operators (`neq`, `not_contains`, `not_in`, `has_none`), never a positive one. Duplicate-phone grouping uses the normalized phone and ignores empty phones. Unsupported operators/values answer 400. The `botId` field (`has_any`, `has_none`) tests `contact_bots`: the bots that ever answered a conversation linked to the customer (T-088), kept when a page moves to another bot.
- Private saved views exist only for their owner (404 for others); shared views are readable by every member and changeable only by the owner (403).
- Creating a contact is idempotent per `clientRequestId`, also under a race.
- **Lead capture (T-102, T-088):** `upsertLeadByPhone(ws, { phoneE164, sourceKey: 'website' | 'facebook' | 'instagram', displayName, firstUrl })` finds the oldest customer with that normalized phone, else creates one (source by built-in key, auto-assignment applies, `contact.created` history, `crm.contact.created.v1` with `origin: 'channel'`, `phoneCaptured: true`, no actor). An existing customer keeps its first source and gets one `contact.updated` history entry (`lead`: null → first URL or `website`). A per-phone advisory transaction lock (`tx.lock`) serializes concurrent captures of one number, so two racing calls end with one customer.
- **PMS link (ADR-017, migration 0051):** `contacts.external_source` + `external_id` link a customer to one PMS customer (unique per workspace). `upsertExternalContact` matches by external id, else the oldest live (not archived) unlinked customer with the normalized phone (it becomes linked), else creates one with the built-in source `kiotviet` ("KiotViet", seeded by key on the first import only, after the defaults), auto-assignment, `contact.created` history and `crm.contact.created.v1` with `origin: 'import'`, no actor. A record without a usable name, phone or email is skipped; an unusable phone, a malformed email or birthday is dropped, not fatal (`domain/external-contact.ts`). The PMS owns name, phone, email, address, birthday and gender of a linked customer: its values overwrite them, nulls included (a value it sent in an unusable form keeps the stored one); a customer adopted by phone only takes the values the PMS has. Only changed fields are written, with one `contact.updated` history entry (no actor, `data.external`), `crm.contact.updated.v1` and a version bump (a stale staff edit answers 409); the same number written differently is no change. Link and unlink are history entries too (`changes.external`), without an event. A link never locks the customer (staff keep editing every field; the next PMS change wins on the PMS fields); a PMS delete or a disconnect only unlinks. External ids are trimmed; an empty one or one over 64 characters answers `VALIDATION_FAILED`. The upsert and `markContactPushed` take the advisory locks `external/<source>/<id>` then `phone/<e164>` (the lead-capture lock; `markContactPushed` takes only the first, before the row lock), so racing imports, captures and push results end with one customer; a unique clash on `contacts_external` is `ContactExternalLinkConflictError`, never a raw error.
- **Push to the PMS:** `contacts.external_push_state` (`pending` while claimed, `failed` when refused, with `external_push_at` and `external_push_error`; null once linked). KiotViet is the only source, so the state carries no source. `claimContactsForPush` moves unlinked, live customers with a usable phone created since `since` from null to `pending` (`FOR UPDATE SKIP LOCKED`, oldest first; the name falls back to the phone as typed). `markContactPushed` links (same id again: no-op; another id: `ContactAlreadyLinkedError`; an id on another customer: `ContactExternalLinkConflictError`). `pushableContact` reads a claimed customer for its push job (null unless still `pending`, unlinked and live). `releasePendingContactPushes` / `staleContactPushes` serve the scan's sweep; `releaseFailedContactPushes` sends `failed` back to null (a full customer import, or the switch turned on again, retries them); `releaseExternalSource` unlinks every customer of the source and clears all push states.
- **Access (T-044):** routes need a capability of the member's role (`@RequireCapability`, `ROLE_CAPABILITIES` in contracts). Without `contacts.view_all` (Sales, CSKH) a member sees only customers they own as Sales or CSKH and unassigned ones; anything else is 404 (list, detail, notes, history, tags). Changing Sales/CSKH needs `contacts.assign`, except claiming an empty slot for yourself. Sharing a view needs `views.share`.
- **Auto-assignment (T-033):** a new customer with a source and no Sales owner goes to that source's enabled policy: weighted round robin over active members, cursor on the policy row (`crm_assignment_policies`, locked while picking, so concurrent creates never share a slot). Only owners, admins and sales can be candidates; removed members are skipped. A Sales/CSKH member who creates a customer without an owner becomes its owner (so it stays visible to them). The history entry carries `autoAssigned: true` and a `crm.contact.assigned.v1` event is written. "By page" and "ratio by day" modes need channels and come later.

**Not yet (later tasks):** tasks/reminders (CRM-05), custom fields, import/merge, files/export/archive, conversation rules, distribution by page or by day, custom roles, analytics projections.

**Do not:** read other modules' tables; put HTTP/Drizzle types in `domain/`; call LLMs outside `ai-core`; send customer messages from CRM actions.

**No database:** routes answer 503 `UNAVAILABLE`. Test with `test/crm.integration.spec.ts`.
