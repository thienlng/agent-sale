# crm

**Purpose:** the shop's customers — profiles with notes and an audit history, customer sources and pipeline statuses, Sales/CSKH ownership, tag definitions with attribute schemas and their assignments, typed filters and saved views (docs/02 CRM-01..CRM-10; GitHub epic #25, issues #26–#29).

**Owned tables:** `contacts`, `contact_notes`, `contact_history`, `crm_sources`, `crm_statuses`, `crm_tags`, `crm_tag_assignments`, `saved_views`, `crm_assignment_policies`, `tasks` (tenant, forced RLS — migrations 0006, 0014, 0051 for the PMS link columns, 0054 for the email adoption index and the SaaS statuses `demo_scheduled` / `free_plan`, 0064 for the request index `contact_history_requests_idx`, 0073 for `tasks`; schema in `packages/db/src/schema/crm.ts`).

**Public API (`api/`):**

- `CRM_FACADE` → `getContact(workspaceId, contactId)`, `ownedContactCounts(workspaceId, userId)` and `reassignContacts(workspaceId, from, to | null, actor)` (used by `team` when a member is removed; history entries are written per customer), and for the inbox: `conversationTags(ws, ids)` (tag chips for list rows), `conversationIdsByTags(ws, { any, all, exclude, untagged })` (id sets the inbox applies to its own query), `upsertLeadByPhone` (lead capture from the website and from phone numbers in Facebook/Instagram messages, below), `recordContactBot(ws, contactId, botId)` (T-088: idempotent, NOT_FOUND for a customer of another business), for the `saas` module (ADR-020): `moveContactStatus(ws, contactId, statusKey, { forwardOnly, keep? })` (system status move by built-in key; `forwardOnly` never moves back in the status order; `keep` leaves a customer at one of these keys) and `addContactNote(ws, contactId, body, authorName)` (system note, a repeat of the latest note is skipped), `listConversationTags` and `assignConversationTag` (the conversation module checks the conversation exists and exposes `/conversations/{id}/tags`), `contactsCreated(ws, {since, until})` (owner reports, T-172: non-archived customers created in `[since, until)`, counted per first source name, `null` = none; counts only), and for `ai` and the owner reports (T-187, below): `recordBotRequest(ws, { kind, details, preview, catalogNames? })` (the bot's `record_request`, used by `ai`, ADR-025; `catalogNames` are the products the bot saw, which fill an empty course or service named in goal or note) and `requestsRecorded(ws, {since, until})` (new requests per kind and per the customer's current status; counts only), and for Today (Business Brain, spec 2026-11-11): `countOpenTasks(ws, { userId?, viewAll?, dueBefore })` and `listOpenTasks(ws, { userId?, viewAll?, limit })` (with `userId`: that user's tasks and the unassigned ones — unless `viewAll`, only unassigned ones whose customer the user may see; without: every open task).
- `CRM_TASK_RUNNER` (`api/crm-task.runner.ts`): `tick(now?)`, run by the `worker` entry every 30 s (due-task reminders, below).
- `CONTACT_SYNC_FACADE` (`api/contact-sync.facade.ts`, used by `integration`, ADR-017, and by `saas` for Rapiz HQ, ADR-021): `upsertExternalContact`, `unlinkExternalContacts`, `claimContactsForPush`, `pushableContact`, `markContactPushed`, `markContactPushFailed`, `releasePendingContactPushes`, `releaseFailedContactPushes`, `staleContactPushes`, `releaseExternalSource`, `linkedContactCount`, `externalIdOf` (rules under "PMS link" below). `ContactDto.external` is `{ source: 'kiotviet' | 'rapiz', id } | null`.
- HTTP (workspace-scoped): `/contacts`, `/contacts/query`, `/contacts/{id}` (+ `/notes`, `/history`, `/tags`, `/requests`), `/crm/requests/summary`, `/tag-assignments/{id}` (+ `/remove`), `/crm/sources`, `/crm/statuses` (+ `/order`), `/crm/tags`, `/crm/assignees`, `/saved-views`, `/tasks` (+ `/{id}`, `/{id}/complete`, `/{id}/cancel`). Contracts: `packages/contracts/src/crm/`.
- Events (outbox, same transaction as the change): `crm.contact.created.v1`, `crm.contact.updated.v1`, `crm.contact.status_changed.v1`, `crm.contact.assigned.v1`, `crm.tag.assigned.v1`, `crm.tag.removed.v1`. Statistics (analytics module) rely on them: `crm.contact.created.v1` carries `origin` and `phoneCaptured`, `crm.contact.updated.v1` carries `phoneCaptured`, and every owner a customer starts with is a `crm.contact.assigned.v1` (not only auto-assigned ones).

**Events consumed:** none yet. Uses the `identity` facade (actor names) and the `workspace` facade (members for assignment, time zone for date filters, account and business name for reminders), and the `notification` facade (due-task reminders).

**Invariants:**

- A contact has at least a name, a usable phone or an email. Phones are stored as typed plus E.164 (`normalizeAnyPhone`); an unusable phone is rejected, not stored.
- Edits carry `expectedVersion`; a stale edit answers 409 and writes nothing. Only sent fields change (`null`/"" clears). "Provided at" timestamps are set when a phone/address first appears and are never touched by other edits. The first source is kept once set.
- Every change appends `contact_history` (field → {from, to}) in the same transaction; status and assignment changes get their own entries and events. Notes are separate from the 500-character profile note; editing a note keeps the old body in the history. Notes never message the customer.
- Sources, statuses and tags have stable ids and are archived, never deleted: archived ones stay on existing customers and in history but cannot be newly chosen. Defaults (7 sources, 8 statuses — 9 SaaS statuses for a `saas` business, ADR-020, and 7 for an `education` or `spa` business, T-187 — 3 system tags) are seeded on first use by `key`. Customer settings (`/app/crm-settings`) is the one place that manages them; CRM, the inbox and statistics read the same ids (T-089). Active tags have distinct names (partial unique index); active sources and statuses too, checked by the service because older workspaces may already hold duplicates, which stay valid until renamed or archived. A clash answers 409 `CONFLICT` with `details.name`. Customer status is independent of the conversation's open/resolved state and of the bot switch.
- A customer's status never changes orders (orders have their own status; nothing in this module reads or writes them).
- Sales and CSKH are separate fields; both must be active workspace members when assigned.
- Classification and attribute tags are active at most once per customer (partial unique index): a retried add returns the existing assignment (200) and a retried remove is a no-op, so neither writes a second event. Work tags may repeat. Attribute values are validated on the server against the tag's fields; fields keep key and type forever and options are archived, never removed, so old values stay readable. Assignments record the schema version they were filled with. Contact and conversation scopes are distinct (`scope`). Conversation tags (inbox v2) use the same library and table with `scope = 'conversation'`; they write no customer history and publish no event, `activeCount` counts customers only, archived tags are hidden from chips and from the `untagged` filter, and removal goes through the shared `/tag-assignments/{id}/remove` route (editing values stays customer-only).
- One SQL compiler (`contact-filter.sql.ts`) builds the WHERE for rows and the total. Null rule: a customer without a value matches `is_empty` and the negative operators (`neq`, `not_contains`, `not_in`, `has_none`), never a positive one. Duplicate-phone grouping uses the normalized phone and ignores empty phones. Unsupported operators/values answer 400. The `botId` field (`has_any`, `has_none`) tests `contact_bots`: the bots that ever answered a conversation linked to the customer (T-088), kept when a page moves to another bot.
- Private saved views exist only for their owner (404 for others); shared views are readable by every member and changeable only by the owner (403).
- Creating a contact is idempotent per `clientRequestId`, also under a race.
- **Lead capture (T-102, T-088):** `upsertLeadByPhone(ws, { phoneE164, sourceKey: 'website' | 'facebook' | 'instagram' | 'bot', displayName, firstUrl })` (`bot`: the SaaS bot tool; no built-in source matches it) finds the oldest customer with that normalized phone, else creates one (source by built-in key, auto-assignment applies, `contact.created` history, `crm.contact.created.v1` with `origin: 'channel'`, `phoneCaptured: true`, no actor). An existing customer keeps its first source and gets one `contact.updated` history entry (`lead`: null → first URL or `website`). A per-phone advisory transaction lock (`tx.lock`) serializes concurrent captures of one number, so two racing calls end with one customer.
- **Bot requests (T-187, ADR-020 generalised; ESV spec §5.1):** a demo, trial, placement test, appointment or consultation the bot records is not a record of its own. `CustomerRequestService.recordFromBot`, in this order: the workspace industry's `REQUEST_PROFILES` entry (contracts `crm/customer-request.ts`) must offer the kind (else `invalid` / `kind_not_offered`, also for every non-request industry); the details parse with `requestDetailsSchema`; unmet required groups are `missing:<first key>`; the phone must normalize; a `preferredDate` before today in Asia/Ho_Chi_Minh is `past_date`; `preview` stops here; the customer is found or created by phone (`upsertLead`, source key `bot`, a `websiteLeadName` placeholder is renamed); then one transaction (`ContactService.applyBotRequest`) locks the customer, treats a request of the same kind within 24 h (`UPDATE_WINDOW_MS`) as an update, whose details are the earlier entry's details with every non-empty new value over them (`mergeRequestDetails`: a new conversation that repeats only what changed keeps the course, service and branch; a new `preferredDate` or `preferredTime` drops both old ones; the note, day label and `missing` follow the merged details, QA retest M5), moves the status (`forward_only` for saas; `unless` the current key is the target or a confirmed `keep` key for education and spa — `decideStatusMove`), appends `contact.request_recorded` or `contact.request_updated` with `data = { kind, details (no phone, no email, empty fields dropped), dateLabel }` and adds the note `requestNote(...)` signed `Bot AI` (`Cập nhật: ` first for an update; the saas text is byte-identical to the ADR-020 `leadNote`). An exact retry inside the window (the latest request entry of that kind holds the same details and day label; notes are not compared, so a staff note in between does not matter) writes nothing. A customer a capture creates in a request industry starts at `new_lead`, and the rename of a placeholder name and the lead marker of one capture are one `contact.updated` entry. `requestsRecorded` takes optional `kinds` (a bookings-only `new_requests` alert). The result lists `missing`: the recommended groups still empty. The `dateLabel` ("Thứ Bảy 07/11/2026") is computed here, never by the model. `GET /contacts/{id}/requests` lists the latest 10 under the customer's visibility; `GET /crm/requests/summary` (`contacts.view_all`, 404 outside saas, education and spa) gives live customers per active status, the open requests (the newest request entry of each customer in 30 days, kept while the customer is still at its kind's target status; max 10) and the new requests of 7 days. Updates never count as new requests.
- **PMS link (ADR-017, migration 0051):** `contacts.external_source` + `external_id` link a customer to one PMS customer (unique per workspace). `upsertExternalContact` matches by external id, else the oldest live (not archived) unlinked customer with the normalized phone (it becomes linked), else creates one with the built-in source `kiotviet` ("KiotViet", seeded by key on the first import only, after the defaults), auto-assignment, `contact.created` history and `crm.contact.created.v1` with `origin: 'import'`, no actor. A record without a usable name, phone or email is skipped; an unusable phone, a malformed email or birthday is dropped, not fatal (`domain/external-contact.ts`). The PMS owns name, phone, email, address, birthday and gender of a linked customer: its values overwrite them, nulls included (a value it sent in an unusable form keeps the stored one); a customer adopted by phone only takes the values the PMS has. Only changed fields are written, with one `contact.updated` history entry (no actor, `data.external`), `crm.contact.updated.v1` and a version bump (a stale staff edit answers 409); the same number written differently is no change. Link and unlink are history entries too (`changes.external`), without an event. A link never locks the customer (staff keep editing every field; the next PMS change wins on the PMS fields); a PMS delete or a disconnect only unlinks. External ids are trimmed; an empty one or one over 64 characters answers `VALIDATION_FAILED`. The upsert and `markContactPushed` take the advisory locks `external/<source>/<id>` then `phone/<e164>` (the lead-capture lock; `markContactPushed` takes only the first, before the row lock), so racing imports, captures and push results end with one customer; a unique clash on `contacts_external` is `ContactExternalLinkConflictError`, never a raw error.
- **Rapiz HQ link (ADR-021, source `rapiz`):** per-source rules live in `domain/external-contact.ts` (`EXTERNAL_SOURCE_RULES`). A platform account links to the customer with its external id, else the oldest live, unlinked customer with the owner's phone, else with the owner's email (`matchedBy: 'email'`), else a new customer with the built-in source `rapiz` ("Rapiz"). The platform owns only phone and email (and the name of a customer that has none), and they are **locked**: a staff edit that changes them on a linked customer answers 400 `VALIDATION_FAILED` with `LINKED_READ_ONLY` per field; the name and every other field stay editable.
- **In the web app:** `ContactDto.external` drives the "KiotViet" / "Rapiz" badge (list and drawer) and the hint on the source-owned fields of the edit form (`apps/web/src/features/crm/components/kiotviet-link.tsx`); KiotViet fields stay editable, Rapiz phone and email are read-only.
- **Push to the PMS:** `contacts.external_push_state` (`pending` while claimed, `failed` when refused, `detached` once the PMS deleted the customer it was linked to, with `external_push_at` and `external_push_error`; null once linked). KiotViet is the only source, so the state carries no source. `claimContactsForPush` moves unlinked, live customers with a usable phone created since `since` from null to `pending` (`FOR UPDATE SKIP LOCKED`, oldest first; the name falls back to the phone as typed). `markContactPushed` links (same id again: no-op; another id: `ContactAlreadyLinkedError`; an id on another customer: `ContactExternalLinkConflictError`). `pushableContact` reads a claimed customer for its push job (null unless still `pending`, unlinked and live). `releasePendingContactPushes` / `staleContactPushes` serve the scan's sweep (the stale list skips archived and phone-less customers); `releaseFailedContactPushes` sends `failed` back to null (a full customer import, or the switch turned on again, retries them); `releaseExternalSource` unlinks every customer of the source and clears the `pending` / `failed` push states. `unlinkExternalContacts` (a PMS delete) marks the customers `detached`: no claim, release, sweep or disconnect touches that state, so a PMS delete is never undone by a push; a later link (import by phone, `markContactPushed`) clears it. A PMS name that is only the customer's own phone (the echo of a customer pushed without a name) never replaces the stored name (`isPhoneName`).
- **Access (T-044):** routes need a capability of the member's role (`@RequireCapability`, `ROLE_CAPABILITIES` in contracts). Without `contacts.view_all` (Sales, CSKH) a member sees only customers they own as Sales or CSKH and unassigned ones; anything else is 404 (list, detail, notes, history, tags). Changing Sales/CSKH needs `contacts.assign`, except claiming an empty slot for yourself. Sharing a view needs `views.share`.
- **Auto-assignment (T-033):** a new customer with a source and no Sales owner goes to that source's enabled policy: weighted round robin over active members, cursor on the policy row (`crm_assignment_policies`, locked while picking, so concurrent creates never share a slot). Only owners, admins and sales can be candidates; removed members are skipped. A Sales/CSKH member who creates a customer without an owner becomes its owner (so it stays visible to them). The history entry carries `autoAssigned: true` and a `crm.contact.assigned.v1` event is written. "By page" and "ratio by day" modes need channels and come later.

- **Tasks (CRM-04, spec 2026-11-11 §4, migration 0073):** a to-do with a title (≤ 200), a note (≤ 2 000), an optional due time and assignee (an active member, checked on create and edit; null = unassigned), links to a customer (must exist and be visible to the creator, else 404), a conversation and a `subjectType` + `subjectId` (opaque ids), and a `source` (`manual`, `today`, `assistant`). Rules in `domain/task.ts`. Any member may create one (`contacts.view`, every role). Without `contacts.view_all` a member sees, edits, completes and cancels only the tasks assigned to them and the unassigned ones whose customer they may see (`canSee`: no customer, or a customer whose Sales/CSKH is them or nobody; anything else is 404); `GET /tasks?scope=all` needs `contacts.view_all` (403). `scope=mine` (default) is "assigned to me + unassigned" for every role. Lists come open first by due time (undated last), `done` lists newest done first; the cursor is an offset. Edits carry `version` (stale: 409). Complete and cancel are idempotent (a retry answers the task as it is); completing a cancelled task or cancelling a done one is 409. `assignee_user_id`, `done_by` and `created_by` have no foreign key: a removed member's id stays, and `assigneeName` is then null. **Reminder:** `TaskReminderRunner` (worker, every 30 s, `app_system`) takes open, assigned tasks with `due_at <= now` and no `reminded_at` (100 per tick), sends the assignee one `task.due` notice in-app and by push (target `/app/today`, `dedupKey task:<id>:due:<due ms>`, text from the i18n `notification` namespace `task.due.*` in the recipient's language), then sets `reminded_at`. An assignee who is no longer an active member is marked without a notice; a failed notice is retried next tick, and after 20 failed ticks (~10 min) the task is marked anyway so failing rows cannot hold the batch. Editing the due time or the assignee clears `reminded_at`: the new due time (or the new assignee) is reminded once. The scan uses the partial index `tasks_reminder_due_idx`. `done_at` is set exactly for done and cancelled tasks (CHECK).

**Not yet (later tasks):** reminder offsets (SET-05), custom fields, import/merge, files/export/archive, conversation rules, distribution by page or by day, custom roles, analytics projections.

**Do not:** read other modules' tables; put HTTP/Drizzle types in `domain/`; call LLMs outside `ai-core`; send customer messages from CRM actions.

**No database:** routes answer 503 `UNAVAILABLE`. Test with `test/crm.integration.spec.ts`.
