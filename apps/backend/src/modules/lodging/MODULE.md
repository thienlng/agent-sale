# lodging

**Purpose:** Places to stay for hotel businesses (T-160, [ADR-018](../../../../../docs/adr/ADR-018-lodging-module.md)): properties sold whole (villa) or per room (homestay) → units → rates (weekday + date-range overrides + surcharges, sell and cost) → nightly calendar → holds, bookings and blocks. Operator guide and API table: [docs/lodging.md](../../../../../docs/lodging.md). Spec: `docs/superpowers/specs/2026-11-01-lodging-calendar-design.md`. Unit details and bedroom packages (T-193): [ADR-027](../../../../../docs/adr/ADR-027-lodging-units-and-packages.md), `docs/superpowers/specs/2026-11-05-lodging-units-and-packages-design.md`.

**Layout:** `domain/` pure rules (nights, rate rules and packages — `assertRateCoverage`, `assertPackages`, `assertRatePackage`, `fullPackage`, `priceFull` —, `quoteStay` with `stayTargets` / `singlePackageTarget`, booking status machine). `application/` services (`PropertyService`, `PropertyRemovalService`, `RatesService`, `LodgingSettingsService`, `BookingService`, `CalendarService`, `NightNotesService`), the bot catalog (`bot-catalog.ts` + pure mapping `bot-product.ts`), the bot holds (`bot-hold.service.ts` + `bot-hold-support.ts`; free-option search shared with the calendar in `availability.ts`) and the store port `ports/lodging-store.ts` (`LODGING_STORE`). `infrastructure/persistence/` Drizzle adapter. `interface/http/` three controllers under `@Controller('lodging')`.

**Depends on:** `workspace` (`WORKSPACE_FACADE`, industry check) and `bot` (`BOT_FACADE`), and on crm only to register on `CONTACT_LIFECYCLE`. Never on `commerce` or any other tier-2 facade.

**Customer deletion (docs/09 §10):** `BookingErasure` (`detach` step): stay bookings linked to the customer (`contact_id`), to one of its conversations or with its phone (digits only) keep their dates and money but get `guest_name = DELETED_CUSTOMER_NAME`, an empty phone and no customer link (version bumped; blocks untouched); the bot's hold drafts of the customer or those conversations are deleted. Store: `BOOKING_ERASURE_STORE`.

**Owned tables** (migrations 0041, 0042, 0043, 0066, 0067 and 0068, schema `packages/db/src/schema/lodging.ts`): `lodging_properties`, `lodging_units`, `lodging_packages`, `lodging_rates`, `lodging_settings`, `lodging_bookings`, `lodging_booking_units`, `lodging_unit_nights`, `lodging_bot_properties`, `lodging_night_notes`, `lodging_bot_hold_drafts`. Also writes `audit_events` (targets `lodging_property`, `lodging_booking`, `lodging_settings`, `bot`) and `outbox_events`.

**HTTP:** `lodgingV2Routes` (`packages/contracts/src/lodging/lodging.routes.ts`). Hotel businesses only (`LodgingAccess.assertHotel`, 404 otherwise).

- `POST /lodging/media/videos` (`catalog.manage`): MP4 upload (`LodgingMediaService`, `interface/http/lodging-media.controller.ts`, own `S3PublicObjectStorage` as `LODGING_MEDIA_STORAGE`, 120 s request timeout, key `lodging/<ws>/<uuidv7>.mp4`). Multipart, one `file` part ≤ 25 MiB buffered in memory, `ftyp` check (`domain/mp4.ts`); 413 `VIDEO_TOO_LARGE`, 400 `INVALID_VIDEO`.
- `DELETE /lodging/properties/{id}` (`catalog.manage`, 204; `PropertyRemovalService`): hard delete under a property row lock. When `lodging_bookings` rows of the property exist (any status, blocks included) it answers 409 `CONFLICT` `details = {reason: 'property_has_bookings', bookings, upcoming}` (`upcoming` = hold/confirmed/checked_in/active not past check-out) unless `?withBookings=true`, which deletes those bookings first (their booking units and unit nights cascade); a racing booking insert without it still hits 23503 → the same 409. Units, packages, rates, night notes, bot properties and bot hold drafts go by `ON DELETE CASCADE`; audit `lodging.property.deleted` `{code, sellMode}` plus `{deletedBookings, deletedUpcoming}` when bookings went too; no event (lodging has no property events). Gallery objects stay in storage (no reference counting; a photo can be shared with a product). Deleting the only property of a bot's explicit list leaves the bot without rows, i.e. selling every active property (the existing "no rows = all" rule). Route `assistant: never`.
- `GET /lodging/bookings/review-count` → `{pending}` (bot holds not reviewed yet); `GET /lodging/bookings?source=bot` filters by source.
- Capabilities: reads `orders.view`; property, room, rate, override and settings writes `catalog.manage`; bot properties PUT `bots.manage`; booking writes and night notes (`PUT properties/{id}/notes`) `orders.manage`.
- Errors: `NOT_FOUND` 404, `VALIDATION_FAILED` 400, `CONFLICT` 409. `NIGHTS_TAKEN` / `STALE_VERSION` answer 409 `CONFLICT` with `details.reason` (and `details.codes` for taken nights).

**Public API (`api/`):**

- `LODGING_FACADE` → `LodgingFacade.listBotPropertyIds(ws, botId)`: the bot's selection, or every active property id when it has none. `stayRevenue(ws, {from, to})`: bookings, nights, revenue (`total_sell`) and profit (revenue − `total_cost`) of the stays (not blocks) in `confirmed`, `checked_in` or `checked_out` checking in on the local nights `from`..`to` inclusive; no guest data (the assistant's scheduled revenue report for a hotel). `latestBookingTimes(ws, conversationIds)` (Business Brain) and `conversationBookings(ws, {since, until, bookingIds?})` (care agent, ADR-031: stays with a conversation in held/confirmed/checked-in/out, created in `[since, until)`, id, time, `total_sell` (0 when unpriced) and status, ≤ 5 000).
- `LODGING_CATALOG_FACADE` → `LodgingCatalogFacade` (`LodgingBotCatalog`): `searchBotCatalog` / `getBotProductsByIds` / `countBotCatalog`, the same shapes as the commerce `CatalogFacade` (structural typing). Each active, fully priced property the bot sells becomes a `ProductDto` with an `accommodation` (`rentalType` `entire_property | rooms`, `rateBasis: 'night'`, whole-place weekday `rates` — its own rules or the per-weekday sum of the active rooms —, room prices in `units`, upcoming overrides with `(min N nights)` in the label, surcharges, policies, media folders as `albums` (photos, videos, links) and their photos flattened as `gallery` (caption or folder name), `imageUrls` cover first; since T-193 units carry their details, own `albums` and `packages`, the whole property's packages are `accommodation.packages` (fewest bedrooms first, `weekdaySell[7]` with null = not sold), weekday `rates` are the full package's and a package override carries `packageName`). Sell prices only, never a cost. Without a database every read answers empty.
- `LODGING_BOT_FACADE` → `LodgingBotFacade` (`LodgingBotHolds`, T-161, spec `docs/superpowers/specs/2026-11-01-bot-lodging-holds-design.md` §3), called by `ai`:
  - `checkAvailabilityForBot(ws, {botId, checkIn, checkOut, adults, childAges, propertyId?})` → nights, Vietnamese weekday labels, `requestedFull`, at most 5 options (fits first, then price; `rankForBot`) with `unitIds`, `unitNames`, `fits`, `overStandard`, `totalSell`, nightly sells with `weekdayLabel`, surcharges in sell only, `minNights` + option `problems: ['min_nights']` when the stay is shorter than a date-range price needs, and `problems` (`invalid_dates`, `invalid_party`, `past_date`, `too_long`, `not_sold`). Properties = the bot catalog's (selection or every active one, fully priced). Options carry `package` (the quote's package when it picked exactly one) and `alternatives {package, bedrooms, totalSell | null, fits}[]`. Checks the bot through `BOT_FACADE`; never throws for the customer's input.
  - `prepareBotHold` → `{status: 'ready', summary, holdMinutes}` or `{status: 'problems', problems, alternatives}`; phone through `normalizeVnPhone` (stored `0xxxxxxxxx`); never writes nights; stores one draft per conversation (30 min, replaces an earlier one) with a sha256 of what the customer saw (`quoteHash`, quote warnings included, plus the `(target, packageId)` list when the quote has packages) and its `packageIds`. Optional `packages: {unitId|null, name}[]` picks packages by name (`pickPackages`, accent-insensitive); problems `unknown_package` (with `validPackages`) and `package_unavailable`; ignored when the stay is priced without any package. A prepare that finds problems (once the dates and party read) deletes the conversation's draft. Summary text: `domain/hold-summary.ts`.
  - `confirmBotHold` → `held {code, holdExpiresAt}` or `expired | no_draft | price_changed | not_available` with alternatives. Locks the draft, re-quotes with the draft's `packageIds` (hash mismatch or a deleted package = `price_changed`), creates the hold through `BookingService.createIn` (status `hold`, source `bot`, actor = the bot's name, `clientRequestId` = uuid v5 of the draft id so a retry replays), and keeps the draft as a tombstone (swept after its 30 minutes): a retried confirm finds the hold by the deterministic request id and answers the same `held`. A check-in already past answers `expired`. On failure the transaction rolls back and the draft (that version) is deleted in a new one; `expired`/`price_changed` offer the same property first when still free, `not_available` the others.
  - `cancelBotHoldDraft`, `hasBotHoldDraft` → `{pending, storedAt}` (a confirmed draft is not pending).
- Events (outbox, `api/lodging.events.ts`), aggregate `lodging_booking`:
  - `lodging.booking.created.v1` `{bookingId, code, propertyId, status, checkIn, checkOut, source}`
  - `lodging.booking.{confirmed,cancelled,expired,checked_in,checked_out}.v1` `{bookingId, code, propertyId}`

**Events consumed:** none.

**Invariants:**

- One `lodging_unit_nights` row per occupied unit-night; its PK `(workspace_id, unit_id, night)` is the only anti-double-booking rule. `takeNights` locks the unit rows (`FOR NO KEY UPDATE`), pre-checks and throws `NIGHTS_TAKEN` with the occupying codes; a racing 23505 maps to `NIGHTS_TAKEN` too. A whole rental of a rooms property takes every active room.
- Occupying statuses: `hold`, `confirmed`, `checked_in`, `checked_out`, block `active`. Cancel, expiry, no-show and block removal delete the nights in the same transaction.
- Lazy hold expiry: every lodging transaction that reads or writes bookings (calendar, availability, quote, booking list/detail/writes, property list, sell-mode check) first runs `expireHolds` — status `expired`, nights freed, history row, `lodging.booking.expired.v1`. No worker sweeps yet.
- A stay lasts 1–60 nights; nights are local dates, check-out exclusive; weekdays are ISO, computed from the date in code; "today" and check-in use Asia/Ho_Chi_Minh.
- Per rate target (whole property or one room) without packages, weekday rules with `package_id` null cover the seven weekdays exactly once. A target with packages: every rate (weekday and override) names one of its packages, the full package (most bedrooms, tie → later `sort_order`) covers the seven weekdays exactly once, the others at most once (a missing weekday = not sold). Overrides never overlap per (target, package) and win over weekday rules. Coverage targets = the active targets plus every target priced in the request; `assertPackages` also accepts the targets of sent packages, so an inactive room's packages survive a save without rates.
- Packages (T-193, ADR-027): price variants of one target, never separate occupancy (a booking takes the unit's nights whatever its package). ≤ 10 per target, distinct bedrooms and names (case-insensitive) per target; a new package needs an active target of this property (the DB cannot check the unit's property). `PUT rates` replaces packages and rates together (`replacePackages` deletes the missing ones — their rates cascade, booking units get `package_id` null — parks kept names under `id::text` to allow swaps, then upserts by id); a kept id may not change its `unitId` (`VALIDATION_FAILED {packageId, unitId}`); stored package-less overrides of a target that gets packages move onto its full package in the same transaction (audit `overridesMoved`). Whole mode drops room packages.
- Quote packages: an explicit `packageIds` entry must belong to a priced target (one per target); otherwise auto. Auto looks at the party only for a single package target (`singlePackageTarget`: the selection prices exactly one target and it has packages) — fewest bedrooms whose `maxGuests ?? standard` holds the party and prices every night, else the full package; any other selection gets each target's full package. An explicit package missing a night → `missing_rate` + `package_unavailable`. Booking edits: `packageIds` omitted = keep the stored packages unless the units changed or the kept quote has `package_unavailable` / `over_max` (then auto), `[]` = auto, else explicit. Blocks ignore `packageIds`. `packageNames` are the current names. Calendar nightly prices use the full package (`priceFull`).
- Create is idempotent by `clientRequestId` (advisory lock + sha256 fingerprint). Only an edit that changes dates, units or party re-quotes at today's rates; only a change of dates or units releases and re-takes the nights (one transaction). Any other edit keeps `unitIds`, `quote` and the nights; its total is the stored base (manual price or `quote.totalSell`) + the new adjustment, unless `manualTotalSell` is sent; a stay without a stored quote (migrated from T-155) keeps `totalSell - adjustment` and `totalCost` as its base. Units compare as a set, child ages in order (web and server alike). An edit that changes dates, units or party of a manually priced stay must send `manualTotalSell` (a number, or `null` for the quote) — checked-in stays too. A checked-in stay may change only `checkOut`, `manualTotalSell`, `adjustment`, `adjustmentReason`, `tags`. Bookings of a paused property stay editable; create is refused.
- `replaceUnits` refuses (409, `details.codes`) to add or reactivate a room while a whole booking that is not checked out has `check_out > today`.
- Early check-out: `check_out` before the booked check-out sets `checkOut = max(checkIn + 1, today)`, releases the later nights, re-quotes an automatic price (keeps it when a night has no rate; total floored at 0) and keeps a manual one; the audit row carries `checkOut {from, to}`.
- A status move or edit of an `expired` hold answers 409 `details.reason = 'HOLD_EXPIRED'` (before the version check, so a hold expired lazily in the same request says so).
- Optimistic `version` on properties and bookings (`STALE_VERSION`).
- Bot holds: a hold with `source = 'bot'` waits for staff while `status = 'hold'` and `reviewed_at` is null; the first staff status action or edit of a bot booking sets `reviewed_at` / `reviewed_by` (a bot actor never does). Bot results never carry a cost, the internal note, night notes or tags.
- Gallery (T-192, ADR-026; every unit gallery too since T-193, error field `units[u].…`): ≤ 20 folders, ≤ 200 items, unique names; Rapiz photos must be `/media/products/<ws>/…`, videos `/media/lodging/<ws>/…` (`IMAGE_NOT_UPLOADED` / `VIDEO_NOT_UPLOADED`); `galleryCover` is '' or an image of the gallery; a flat pre-0066 list reads as one "Ảnh chung" folder (`toGallery`). Removing an item never deletes its object.
- Status moves follow `domain/booking-status.ts` only.
- Event payloads never carry the guest's name or phone. Bot products never carry a cost, the property's `internalNote`, night notes or booking tags (`bot-product.ts` maps none of them; `bot-catalog.spec.ts` asserts the internal note).
- Night notes (`lodging_night_notes`): one per (property, unit or null, night), text 1–300 chars; an empty text deletes; a `unitId` must be a room of a rooms property. Staff-only, internal.
- Booking tags: ≤ 8, each ≤ 30 chars, NFC-normalised, trimmed and de-duplicated by `normalizeTags` (= contracts `normalizeBookingTags`, also used by the web tag editor); stays only (a block has none); a checked-in stay may change them; labels only, never part of pricing. `listBookings` filters with `tags @> array[tag]`.
- A new property is added to every bot that has an explicit property list.
- After a store error (`NIGHTS_TAKEN`, 23505, 23503) the transaction is aborted: never keep using it.

**Do not:** read or write other modules' tables; import `commerce`; put HTTP or Drizzle types in `domain/`; call LLMs; query rates per property in a loop (use `ratesByProperty`).
