# conversation

**Purpose:** The multichannel inbox: conversations and messages per customer, staff sends, human takeover and the bot reply pipeline for Meta events.

**Owned tables:** `conversations`, `conversation_messages` (schema in `packages/db/src/schema/conversation.ts`, migrations 0007, 0024). `conversations.data` is the document; the index columns (`unread_count`, `awaiting_since`, …) are derived from it by the store on every save and are what the list filters on.

**Public API (`api/`):**

- `CONVERSATION_FACADE` → `list(ws, query, viewerId)` (filters, tabs, counts), `get`, `update` (incl. `assigneeId`), `markRead`, `markUnread`, `linkLead`, `setContact` (HTTP only), `addNote`, `refreshCustomerProfile`, `listTags`, `addTag`, `send`, `receive`, `getReplyContext`, `botHolds` (bot still holds the conversation; the agent loop's interrupt check), `commitBotReply`, `commitBotFollowUp`, `handOff`, `commitBotAttachments` (typed `image | video`, a video alone), `awaitingReply(ws, {olderThan, limit ≤ 200})` (owner reports, T-172: open conversations with `awaiting_since <= olderThan` on the waiting index; the count, the oldest wait, the split by channel kind (`data.provider`) and the oldest ids for an alert fingerprint; no customer data), `signalContext(ws, id, after)` (Business Brain: the delivered messages after `after`, last 40 / 8 000 chars, and the conversation facts; null when not in the workspace), `todayCandidates(ws, {ids, awaitingBefore, followUpBefore, limit ≤ 1 000})` (Today screen: the given conversations plus the open ones waiting since `awaitingBefore` and those with a reminder due by `followUpBefore`, spam left out; facts only, with the time of the last delivered staff message), `followUpFacts(ws, id)` (care agent: status, mode, provider, last customer / staff message times — the staff time by one max query — last sender), `commitCareMessage(ws, id, {text, idempotencyKey, anchorAt})` (care agent, ADR-031: a bot message marked `source: 'care'`, never a tag; does not change the mode; refused with CONFLICT and `details.reason` — `conversation_closed`, `window_closed`, `customer_replied` (the customer wrote after `anchorAt` or is waiting), `taken_over` (mode not `bot`) — checked in the reserving transaction), `aiTouches(ws, points ≤ 1 000, windowMs)` (attribution, per sale in SQL: the first delivered bot message in the window before it and whether staff wrote after it; no text)
- `CONVERSATION_RUNNER` (`MetaInboxProcessor.tick`) — run only by the `agent` entry.
- HTTP: `/conversations`, `/conversations/{id}`, `/conversations/{id}/messages`, `/conversations/{id}/read`, `/conversations/{id}/unread`, `/conversations/{id}/notes`, `/conversations/{id}/tags` (GET, POST; the tag library is crm's, removal via crm's `/tag-assignments/{id}/remove`).

**Events published (outbox):** `conversation.message.received.v1` (+ `channelId`, `occurredAt`, `firstMessage`), `conversation.reply.reserved.v1`, `conversation.reply.completed.v1` (+ `channelId`, `sender`, `occurredAt`), `conversation.control.updated.v1` — statistics read the first and third.

**Events consumed:** none (claims `channel_webhook_events` through the channel facade).

**Hooks:** registers a `BOT_LIFECYCLE.onDeleted` handler that clears `conversations.bot_id` for the deleted bot in that workspace (`releaseBot`; bots are soft-deleted, so the column's `ON DELETE SET NULL` never fires — ADR-012 §4).

**Invariants:**

- Every receipt is persisted before inference; a burst is answered once, for its newest customer message in **receipt order** (claim order), never Meta timestamps. The model gets all messages in that order and every consecutive customer message after the last bot/staff message **of any status** (sent, failed, pending, unknown: a reply attempt, even a failed one, means the earlier messages were answered; only sent text is shown to the model as an assistant turn) is merged into ONE customer turn (newline-joined, attachment notes once, `jobs/reply-turns.ts`), so one reply answers every question after the last reply; a message claimed in a later tick gets its own reply; a retry of an event whose reply was already attempted (last stored message is outbound) is skipped, never answered or sent twice. A skipped customer message is logged with its reason.
- Message ids are monotonic UUIDv7 (`nextMessageId`), so "newest" and "already answered" are decided by storage order, not by Meta timestamps or `createdAt` (which is the Meta time for inbound).
- Customer images: with `BOT_IMAGE_VISION` on, the newest 3 image attachments of the pending turn are fetched by the SSRF-safe `SafeImageFetcher` (Meta CDN allowlist, `BOT_IMAGE_EXTRA_HOSTS` for tests, never logged or stored) and sent with the turn; failures degrade to the text-only note/handoff below.
- Media the model cannot see: a text message with attachments carries an explicit note in the customer turn; media-only unanswered content gets the bot's `handoffMessage` once and the conversation switches to `human`.
- Bot pictures: after the text reply is committed, the processor sends each `images` entry of the AI answer (max 3) through `commitBotImage` (attachment `image`, empty text, key `bot:<event id>:img<n>`), sequentially. It needs only that the bot still holds the conversation (no revision check: the text reply already bumped it) and the open 24-hour window. A failure is a failed/unknown outbound message, never an event failure, retry or handoff; a null result (takeover, bot off) or a closed window stops the remaining pictures.
- Agent sends (harness v2, spec §7, `jobs/reply-delivery.ts`): each turn gives the AI a `MessageSink`; every `send_message` is delivered at once through the same reserve → deliver → record path (keys `bot:<event id>:s<n>`, `:s<n>:t2`… bubbles, `:s<n>:img` album of up to 8 pictures (`MAX_BOT_IMAGES`) with the single-picture fallback, `:s<n>:vid` video message; text → album → video, or album → video → text when the text carries quick replies), at least 800 ms after the previous send (the final answer included), and nothing more goes out after a takeover, an undelivered message or a newer customer message. The final answer follows with the usual keys; a turn that sent nothing gets the bot's fallback message. `shouldInterrupt` = a newer queued customer event (`hasNewerCustomerEvent`) or `botHolds` false; an interrupted turn hands its event back (`requeueEvent`) with the run's `carry` kept in memory per conversation, and the next claim re-runs it with every customer message of the burst (only a fresh carry of an interrupted run hides the bot messages it covers; a re-run without one keeps every earlier send as plain history), at most 3 re-runs per burst, the last one without an interrupt check. A pending re-run is dropped when its event is skipped or staff wrote after it. A first send that throws before anything was stored fails the event (retry, then staff) instead of dropping it. Comment replies get no sink and no interrupt. The processor passes `sentMediaUrls` (URLs of bot attachments sent in the last 30 days among the newest 200 messages of the loaded context, `sentBotMediaUrls` in `jobs/reply-turns.ts`) to the ai reply; bot and staff attachments appear in the history as "[Bot đã gửi N ảnh]" / "[Nhân viên đã gửi …]" (`outboundAttachmentNote`).
- A staff send or an unmatched Meta echo pauses the bot (`mode: human`, optional auto-resume per bot settings). A bot reply is dropped if control or revision changed after generation.
- The echo of an uncertain (`unknown`/`pending`) send is matched by text and attachment count, not treated as a staff reply.
- Only a customer message opens the 24-hour window. A message is either text or one HTTPS attachment.
- `HUMAN_AGENT` (ADR-031): with `META_HUMAN_AGENT_TAG=true`, a member's own `send` on Messenger/Instagram between 24 hours and 7 days after the customer's last message goes out with the tag (`replyWindow` in `packages/channels`; the message stores `tag: 'HUMAN_AGENT'`). Bot replies and care messages never get it; after 7 days (or with the flag off, after 24 hours) the send is refused (409).
- Metering (T-091, ADR-012 §5): before asking the AI, a customer reply reserves one unit of the account's allowance through the `billing` facade, keyed by the reply's outbound idempotency key (`bot:<event id>`, `comment:<comment id>`), so retries count once. A `sent` reply captures it; a failed delivery, an AI error or a dropped reply releases it; an unknown/pending delivery keeps the reservation until it expires (15 min). With the allowance spent, the AI is not called: Messenger/Instagram/website get the bot's hand-off message and the conversation switches to `human`; a fanpage comment goes to staff review. Media-only and provenance hand-offs are not billed.
- Failed processing retries after 20 s, then 60 s; after the last attempt the conversation is handed to staff.

- Read state is shared by the shop and never bumps `revision` or `updatedAt`. `awaitingSince` is set by a customer message and cleared by any outbound one (human, bot or staff echo).
- The agent entry calls `refreshCustomerProfile` (not awaited) after each customer message; it stamps `profileFetchedAt` first, so Meta is asked at most once a day after a success and every 15 minutes after a failure, and it never throws.
- **Customer link (T-088):** `contactId` lives in the `contact_id` column (composite key to the business's contacts, cleared if the customer row goes). `PUT /conversations/{id}/contact { contactId | null }` (`contacts.edit`) checks the customer through `CrmFacade.getContact` first. After a stored Facebook/Instagram customer message, a conversation with a (non-placeholder) phone and no customer is linked to the customer with that E.164 phone, created through `upsertLeadByPhone` when missing; an existing link is never replaced. Linking and a change of answering bot call `CrmFacade.recordContactBot`. The automatic part is best effort: a failure is logged and never fails the message. Each link writes `conversation.contact.linked.v1` `{ actorId, contactId, origin: staff | lead | phone }`. `GET /conversations?contactId=` lists a customer's conversations.
- **Website lead (T-102):** `linkLead(ws, id, { contactId, phoneE164, capturedAt })` (called by webchat) stores `lead` `{ contactId, phone, capturedAt, seenAt: null }` in the conversation document and sets `contactId`; it is idempotent for the same contact and phone and, like read state, never bumps `revision` or `updatedAt`. `markRead` sets `lead.seenAt` the first time staff open the conversation (the inbox "Số mới" badge is `lead && !lead.seenAt`). When `lead` is set the bot's reply request carries `phoneKnown`, and the AI prompt gets one extra system line telling it not to ask for the phone number again.
- Tag chips are filled from `CrmFacade` on list, detail and mutation responses and are never stored; tag filters ask crm for id sets (`idsIn`/`idsNotIn`) that the SQL query applies.
- Assignees are validated through `TeamFacade` (active members only), names come from `IdentityFacade`.
- **Staff alerts (T-190, `application/inbox-alerts.ts`):** `handOff` raises `inbox.handoff`, and a stored customer message (not an echo) in a `human`-mode conversation raises `inbox.message`, through `NOTIFICATION_FACADE` (`in_app` + `push`, target `{kind:'conversation'}`). Recipients: the active assignee, else every active member with `contacts.edit` (owner first, max 20). Dedup `inbox:<conversationId>:<n>` per user (`n` = the revision for a handoff, the 5-minute window for messages), so a burst alerts once. Spam conversations never alert; an alert failure is logged (ids and error class only) and never fails the inbox operation. Uses the `workspace` facade (account, members, business name) for it.

- **Inbox guards (security audit #2, #3, #18; `application/inbox-guards.ts`, all limits on the shared limiter, `0` = off):**
  - The meta inbox claims 25 events per tick with at most `INBOX_CLAIM_PER_WORKSPACE` conversations per workspace and runs up to `INBOX_CONCURRENCY` conversations at once; events of one conversation still run in order. A tick lasts as long as its slowest turn.
  - Each workspace has a TenantFairness token bucket (`INBOX_TURNS_WORKSPACE_MINUTE`, burst `INBOX_TURNS_WORKSPACE_BURST`); a turn over it is deferred, not failed.
  - At most `CONVERSATION_BOT_REPLIES_HOUR` bot replies per conversation and hour; the next turn hands the conversation to staff.
  - Anonymous website visitors (no lead, no contact) get AI replies within `WEBCHAT_AI_REPLIES_SITE_HOUR|DAY` per site and `WEBCHAT_AI_REPLIES_WORKSPACE_HOUR|DAY` per workspace. Past a cap the visitor gets the bot's hand-over message once per conversation and day, with no model call, no credit and no hand-off; the active owners get one `inbox.ai_capped` notification per scope and window.

**Do not:** read other modules' tables; put HTTP/Drizzle types in `domain/`; call LLMs outside `ai-core`.
