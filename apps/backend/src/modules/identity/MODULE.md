# identity

**Purpose:** users, password login, sessions (refresh-token rotation) and access tokens; owns the single global `AuthGuard` that authenticates every non-public route and enforces workspace membership on `@WorkspaceScoped()` routes.

**Owned tables:** `users`, `sessions` (global, app_system only — migration 0001), `user_mfa` (migration 0018), `email_codes` (migration 0056), `user_identities` (migration 0072), `auth_counters` and `trial_claims` (migration 0077), `user_security_events` (migration 0078; global, app_system only, append-only); schemas in `packages/db/src/schema/identity.ts`. Migration 0078 also adds `sessions.authenticated_at`, `sessions.mfa` and `sessions.stepped_up_at` and the `reauth` email-code purpose.

**Public API (`api/`):** `IDENTITY_FACADE` (bootstrap helpers; `profile(userId)` → `{ name, email, locale }` with `locale` `vi` unless the user chose `en`, used by `notification` for the recipient's address and language, T-172) and, for the platform admin only, `IDENTITY_ADMIN_FACADE` → `usersByIds(ids)`, `searchUsers(q, limit)` (email/phone/name substring) returning `{ id, name, email, phone }`. `IDENTITY_DELEGATION_FACADE` → `delegate(authorization, ttlSeconds)`: a short-lived (≤ 10 min) access token of the same user and session, claim `dlg`, for the owner assistant's in-process route calls that may outlive the caller's token (ADR-024); a delegated token cannot be delegated again. Other modules use `@Public()`, `@WorkspaceScoped()`, `@CurrentUser()`, `@CurrentWorkspace()` from `common/http/auth-context.ts`. HTTP: `/auth/signup|login|refresh|logout`, `/auth/signup/code`, `/auth/signup/business`, `/auth/password/forgot|reset`, `/auth/providers`, `/auth/google/start|callback|mfa|verify`, `/me`, `/bootstrap`, `/auth/mfa`, `/auth/mfa/setup|enable|disable|recovery-codes`, `GET|POST /auth/reauth`, `POST /auth/reauth/code`, `GET /auth/identities`, `DELETE /auth/identities/:provider/:subject`. Decorators for other modules also include `@RequireRecentAuth()` (step-up, below). `ApiKeyService.revokeAllCreatedBy(userId)` revokes every key a user created (contracts in `packages/contracts/src/identity/`).

**Events consumed:** none. Uses the `workspace` facade (create the first business in onboarding, membership lookups), the `billing` facade (the first business starts the account's trial; a failure is logged and never blocks it), the `MAILER` port (`common/email`, Resend in production) and the `account` facade (bootstrap lists the user's accounts and the account name of every business, so the web groups businesses by account; a member sees the owning account's name, nothing else about it).

**Invariants:**

- Passwords: Argon2id; 8–128 chars; not common; not equal to email/name. Unknown email and wrong password give the same error and cost the same time.
- Access token: EdDSA JWT, 15 min, claims `sub` (user) + `sid` (session). Refresh token: 32 random bytes, stored only as sha256, 30 days, rotated on every use; presenting a retired token revokes the whole family.
- Web clients get the refresh token only as an HttpOnly cookie scoped to `/api/v1/auth`; cookie refresh checks `Origin` against `APP_ORIGINS`. Native clients use the body (`client: native`).
- A workspace the user is not a member of answers 404, never 403, with `details.reason = 'workspace_access'` so the client can tell a lost business from a missing resource (it reloads bootstrap; T-079). The reason reveals nothing: the same answer is given whether the workspace exists or not.
- Platform admin (`users.is_platform_admin`) is set only by the CLI (`pnpm --filter @agent-sales/backend platform-admin grant|revoke <email>`), exposed read-only as `UserDto.isPlatformAdmin`, and re-checked in the database on every `@PlatformAdmin()` request (non-admins get 404). An admin also needs two-factor **on** (403 `admin_mfa_required`) and a session that **passed** it — a login code, a TOTP step-up, or enabling two-factor on that session (403 `mfa_session_required`); the first is read from the database on every request, the second whenever the cached session state does not already show it. Rollout: `docs/runbooks/platform-admin-2fa.md`.

- **Tokens die with their session (security audit #10, R4):** after verifying the JWT the guard loads the session (`SessionService.state(sid)`): a missing, revoked or other-user session answers 401 `details.reason = session_revoked`. The lookup is cached per process for `AUTH_SESSION_CACHE_TTL_MS` (default 15 000 ms; `0` disables), so a revocation reaches every API process within that time instead of the 15-minute token life; the revoking process drops its own entry at once. Logout revokes the session's whole refresh family. Delegated tokens (`dlg`) carry the same `sid` and die with it, and never pass a `@PlatformAdmin()` or `@RequireRecentAuth()` route (404): the assistant only calls workspace routes of its catalog (`assistant.use` read/write), and every step-up workspace route is `assistant.use: never`.
- **Step-up (`@RequireRecentAuth()`, `application/step-up.ts`):** the session's `authenticated_at` (set by login, signup, Google sign-in and `POST /auth/reauth`; kept on refresh rotation) must be within `AUTH_STEP_UP_WINDOW_MINUTES` (default 10), else 403 `reauth_required`. Used on API key creation, data export creation, `DELETE /auth/identities/…`, the back office payment, plan, billing-settings and account plan/trial/override/status/payment writes, and every `/admin/llm` write (providers, model discovery, Hermes login, tiers). `POST /auth/reauth` takes exactly one proof, chosen by the account: a TOTP or recovery code when two-factor is on (also marks the session `mfa`), else the password, else a code emailed by `POST /auth/reauth/code` (purpose `reauth`); a Google-only user can also sign in with Google again (a fresh session). Wrong proofs answer 400 `invalid_password|invalid_code|code_invalid|code_expired` and are throttled like the two-factor checks. `GET /auth/reauth` returns `{ methods, recent, mfa, recentUntil, hasPassword }`. `POST /auth/reauth` (and only it) also sets the session's `stepped_up_at` (kept on refresh rotation). The web client prompts on 403 `reauth_required|step_up_required|mfa_session_required` and retries once, only for a replayable body (JSON or a `Blob`; `setStepUpHandler`, `components/step-up-dialog.tsx`). A stolen access token can spend the user's step-up and two-factor attempt budget (`mfa:<userId>`, shared with login codes); see docs/09 §2.
- **Users without a password (Google only)** have no password to give (`MfaSetupRequest.password` / `MfaReauthRequest.password` optional). Turning two-factor **on** needs an explicit step-up within the window (`stepped_up_at`: an emailed code via `POST /auth/reauth`); a recent sign-in alone does not count, so a stolen access token of a fresh Google session cannot turn it on and lock the owner out — 403 `step_up_required` (the web prompt then offers the emailed code only: a new Google sign-in opens another session). Turning it off or replacing recovery codes needs a session that passed two-factor within the window (its sign-in or a TOTP step-up; 403 `reauth_required`) plus the current code the action asks for.
- **Security log and notices (`application/security-events.ts`):** `user_security_events` records `password.reset`, `mfa.enabled|disabled|recovery_codes_replaced|recovery_code_used`, `identity.linked|unlinked`, `session.revoked`, `session.step_up`, `api_key.created|revoked` with ids and counts only (no codes, tokens, passwords or addresses) and the client IP. A password reset and every two-factor change also email the user a notice (turning two-factor on mails it before the other sessions are revoked). Recording or mailing never fails the action (logged by error class only).

- **Two-factor (ADM-04):** TOTP (RFC 6238, SHA-1, 30 s, 6 digits, ±1 step). The secret is sealed with `SecretBox` (`SECRETS_ENCRYPTION_KEY`); recovery codes (8, `xxxxx-xxxxx`) are stored only as sha256. A setup is pending until the first valid code; only then does login ask for a second factor. A code is accepted once (`last_used_step` advanced atomically); a recovery code is burned atomically. Login without a code answers 401 `details.reason = mfa_required`, a wrong one `mfa_invalid`; the per-IP+email attempt counter is only reset after the second factor passes. Setup needs the password; disabling and replacing recovery codes need password + a current code (400 `invalid_password|invalid_code`, not 401, so the session survives). Lost phone and codes: operator runs `pnpm --filter @agent-sales/backend mfa-reset <email>`.

- **Email verification (ACC-01, ADR-023):** `/auth/signup/code` (public, rate-limited per IP) emails a 6-digit code (sha256 of email + purpose + code in `email_codes`, 15 min, 5 wrong tries then `code_expired`, a new code at most every 60 s → 429 with `retryAfterSeconds`). `/auth/signup` needs the code (400 `code_invalid|code_expired`) and creates the user verified, with no business. `/auth/signup/business` creates the first account + business + trial, 409 `account_exists` once the user owns an account.
- **No signup enumeration (migration 0077):** `/auth/signup/code` answers 204 for a registered address too; that address gets `accountExistsEmail` (no code) and a decoy code row is stored, so cooldown, caps and wrong-guess answers look the same. `/auth/signup` consumes the code before checking the email, so 409 `email_taken` is left only for a race. The `name` field is ignored; code emails never carry requester text.
- **Auth counters (`WindowCounter` port, `AUTH_COUNTER`, `application/auth-limits.ts`):** fixed windows shared by every replica (`PostgresWindowCounter` on `auth_counters`, sha256 keys; in-memory without a database). Code emails: 3 per inbox per hour, 5 per day (429), counted per purpose (`signup` with the account-exists notices, `reset_password` apart) and keyed on `canonicalMailbox` (`domain/mailbox.ts`: `+tags`, Gmail dots and googlemail.com fold into one inbox; code rows stay on the exact address). Code checks: 5 wrong guesses per code, reserved atomically on the counter (key per code hash, 15 min window), then `code_expired` even for the right code; a new code starts a new budget, so the email caps bound the total. The wrong guess that kills a reset code emails the owner `codeGuessAlertEmail`, at most once per inbox per day. The counter's sweep of ended windows runs best effort in its own transaction (`for update skip locked`). Login: 20 per normalized email per hour on any IP (429), cleared by a successful login or password reset; the per-IP+email `AttemptLimiter` stays. Google sign-in does not reset the login lock (it does not go through the lock either). The lock never blocks recovery: reset codes have their own caps and per-code guess budgets, so the owner can always reset within one email-cap window (an hour, at worst a day when an attacker filled the daily reset cap).
- **One trial per person (`domain/trial-identity.ts`):** the first business starts the trial only if the owner's canonical email (`canonicalMailbox` in `domain/mailbox.ts`: lower case, no `+tag`; Gmail without dots, `googlemail.com` → `gmail.com`) is claimed in `trial_claims` for that user and the domain is not disposable (built-in list + `TRIAL_BLOCKED_EMAIL_DOMAINS`). The account is created either way. If the claim was written but starting the trial then fails, a warning is logged (workspace and user id, no email) so an operator starts it from /admin.
- **Password reset:** `/auth/password/forgot` answers 204 for any email (no enumeration; rate-limited per IP; within the cooldown or over the reset caps nothing is sent and it still answers 204); `/auth/password/reset` (rate-limited per IP + email) checks the code and the password policy, sets the password and revokes every session of the user (their access tokens stop at once, see above). It also removes every linked Google sign-in (`user_identities`) and revokes every API key the user **created**, in every workspace (`CredentialResetService`): a reset is how a takeover is recovered, so nothing the attacker may have attached survives it. Keys created by other members are untouched. The user gets a notice email and a `password.reset` event with the counts.

- **Google sign-in (ADR-007, `application/google-sign-in.ts`, `interface/http/google-auth.controller.ts`):** authorization code + PKCE (S256) + `state` + `nonce`, run on the server. `/auth/google/start?redirect=` seals `{state, verifier, nonce, redirect, exp}` with `SecretBox` into the cookie `rapiz_google` (HttpOnly, SameSite=Lax, path `/api/v1/auth/google`, 10 min) and redirects to Google. `/auth/google/callback` checks the state against the cookie (constant time), exchanges the code, verifies the ID token with Google's keys (`HttpGoogleOAuthClient`: issuer, audience, RS256, required `exp`/`iat`/`sub`, 30 s clock tolerance; logs only Google's token-endpoint `error` word or jose's error code), the nonce and `email_verified`, then resolves the user: linked `sub` → that user; else the user with the same email, only when Google is authoritative for it (`@gmail.com`, or `hd` claim = the address's domain; otherwise `account_exists`), and an unverified one loses its password and every session; else, when Google is authoritative for the address, a new password-less, verified user; when it is not (a custom domain without a matching `hd`), the account is created only after the code emailed to the address (purpose `signup`) is entered: the callback seals a 15-minute `rapiz_google_verify` ticket (subject, address, name, redirect), lands on `/login?google=verify`, and `POST /auth/google/verify` (Origin-checked) consumes the code, creates the user, links the `sub` and signs in (security audit #8: a Google account on someone else's domain cannot pre-create, and later own, an address it does not control). Every completed sign-in upserts `user_identities` (a `sub` linked to another user is never moved). With TOTP on, a sealed 5-minute ticket (carrying the pending link) goes to `rapiz_google_mfa` and `POST /auth/google/mfa` (Origin-checked) needs a code; the link and the unverified-address claim are applied only after it; else the refresh cookie is set. Linked sign-ins are listed by `GET /auth/identities` and removed by `DELETE /auth/identities/google/:subject` (step-up; 409 `last_sign_in_method` when it is the only way in; 404 for an unknown link or provider). The browser always lands on `/login` with `google=done|mfa|verify` or `google_error=cancelled|expired|unverified_email|account_exists|unavailable|too_many|failed` and `redirect` (same-app paths only: no `//`, backslash, space or control character). Callbacks with a live flow are rate-limited per IP on `GOOGLE_CALLBACK_LIMITER` (60 per 15 min, reset by a completed sign-in). Unexpected errors are logged as class name + SQLSTATE, never the message. Password login of a password-less user fails like a wrong password, at the same cost. Config: `GOOGLE_CLIENT_ID` + `GOOGLE_CLIENT_SECRET` (both or neither; unset → `/auth/providers` says `google: false`), `GOOGLE_REDIRECT_URI` (default first `APP_ORIGINS` + `/api/v1/auth/google/callback`).

**Do not:** read `users`/`sessions` with the tenant connection; log tokens or passwords; add a second global guard.

**Test:** `pnpm --filter @agent-sales/backend test -- identity` and `pnpm test:integration`
