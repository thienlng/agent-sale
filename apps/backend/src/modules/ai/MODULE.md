# ai

**Purpose:** the bot's reply pipeline (today: the dashboard playground), the runtime LLM gateway built from the platform's LLM configuration, the back-office API that manages that configuration, and `ai_runs` metering.

**Owned tables:** `ai_runs` (tenant, forced RLS), `conversation_summaries` (tenant, forced RLS, migration 0037), `llm_providers` and `llm_tier_routes` (global, `app_system` only) — migration 0003; schema in `packages/db/src/schema/ai.ts`.

**Public API (`api/`):**

- `AI_FACADE` → `AiFacade.playground(workspaceId, botId, input)` — one test reply; `reply(workspaceId, botId, input, options: ReplyOptions)` (channels: `{ conversationId, isTest, sink?, shouldInterrupt?, carry?, turnTimes? }`) returns `ReplyResult` (`PlaygroundResponse` + `carry` on interrupt + `askedConfirmation` when the turn stored an action confirmation question), see below; `discardPendingConfirmation(workspaceId, conversationId)` — drops that question when the caller did not deliver the answer that asked it.
- HTTP: `POST /bots/{botId}/playground` (workspace-scoped); `/admin/llm/providers…` (incl. `GET|POST|DELETE /admin/llm/providers/{id}/hermes-login`: ChatGPT device-code sign-in of a `hermes` provider, proxied to the bridge's `/v1/auth/*`; bridge down = `{state:"unreachable"}`; gated by `HERMES_SUBSCRIPTION_LOGIN`, default off in production: GET returns `{state:"disabled"}`, POST/DELETE 403 `FORBIDDEN`; logout is local only), `GET /admin/llm/providers/{id}/models` (bridge `/v1/models`) and `/admin/llm/tiers…` (`@PlatformAdmin()`). Contracts: `packages/contracts/src/ai/`.
- Events: none yet.

**Events consumed:** none. Uses the `bot`, `knowledge`, `workspace`, `commerce` and `action` facades.

**Invariants:**

- LLM calls go through `packages/ai-core` providers only, via `LlmRuntime`; the tier → provider/model mapping comes from the database, never from env or code.
- API keys are sealed with `SecretBox` before they are stored and are never returned (only `apiKeyHint`).
- Every admin write calls `LlmRuntime.invalidate()`; other processes pick changes up within 10 s.
- A tier without a usable route is `AI_UNAVAILABLE` (503) in production; elsewhere the deterministic `dev-fake` provider answers.
- Reply path (agent harness v2, spec `docs/superpowers/specs/2026-10-31-agent-harness-v2-design.md`): `PlaygroundService.reply(ws, botId, input, options: ReplyOptions)` runs `application/agent-loop.ts` (`runAgentLoop`: at most 10 rounds, 120 s budget with a wrap-up notice at 80 %, per-call timeout, interrupt checks) with the tools of `application/reply-pipeline.ts#turnTools`: `search_products`, `product_details` (read-only, `application/catalog-tools.ts`), `send_message` (not offered for fanpage comment replies) and `handoff` (`application/output-tools.ts`), then the action tools. The model answers in free text: no JSON envelope, no `responseFormat`, no format retry, no prose salvage. The number guardrail (`domain/grounding.ts#ungroundedFigures`) is no longer applied to replies; the module and its tests stay.
- Outcome (`reply-pipeline.ts#decideReply`): `handoff` when the handoff tool ran (final message = the model's lead-in line, if any, then the bot's handoff message) or the provider refused (`provider_refusal`); `answered` when anything reached the customer (a `send_message` or a non-empty final text); otherwise `fallback` with the bot's fallback message (built-in when empty). Loop limit (`tool_loop_limit`), repeated invalid tool batches (`invalid_tools`), the time budget (`budget`), truncated output (`output_truncated`) and the action limit (`action_loop_limit`) never send model text: the fallback message goes out unless a `send_message` already did. Fallback text is never model text.
- `send_message({text?, imageIds?})`: text ≤ 2 000 chars, ≤ 3 image ids per call, several calls per turn allowed (no per-turn picture cap). Ids resolve only against the turn's allowlist (`ImageAllowlist`: focus products, image-library matches, products whose details a tool returned this turn, and the products named in an interrupted run's carried tool results); unknown ids are dropped and listed in the tool result (`droppedImageIds`). With `options.sink` the message is delivered at once (the caller's channel delivery; `delivered: 0` = not sent, e.g. takeover); without a sink (playground) it is collected. The final text is NOT sent through the sink: the caller sends it (`messages[].via = 'final'`).
- Response (`ReplyResult`): `messages` (every message in order, `via: 'send_message' | 'final'`), `steps` (kinds and tool names only), `interrupted` and, on interrupt, `carry` = the loop's follow-ups (already including the input carry) for the caller's re-run; `reply` = all sent texts joined by `\n`; `images` = every sent picture (contract cap 30). An interrupted turn has no final message and records its run (`guardrail: interrupted` when nothing was sent). A pending confirmation stored in a turn that is interrupted or reaches nobody is cleared.
- Context (`application/reply-context.ts`): the system prompt is byte-stable per bot (prompt, bot settings, style); every per-turn block (business profile, knowledge, situations, focus products, pending action, picture list, the phone-known line, `<current_time>` in Asia/Ho_Chi_Minh) rides on the last user message. `promptCacheKey = ${botId}:${conversationId ?? playgroundConversationId(botId)}`. Long histories (> 24 000 chars) keep the last 12 turns and replace older ones by `<earlier_conversation_summary>` (`context-compression.ts`, `history-summarizer.ts`, bot tier); the summary is stored per conversation (`conversation_summaries`, `CONVERSATION_SUMMARY_REPOSITORY`) only when the caller passes `options.turnTimes` (sent time of each input message), otherwise it is computed for the turn only. A summarizer failure keeps the full history (log: error class only). Consecutive user messages are merged.
- Metering: one `ai_runs` row per turn with usage and latency summed over every model call (summarizer included). When a model call throws and nothing was sent yet, a run with `outcome: fallback`, `guardrail: model_error`, the usage spent so far and the products already seen is recorded (if any call succeeded), then the error is rethrown. When a `send_message` was already delivered, the turn does not throw: it returns `outcome: answered`, `guardrail: model_error` and the messages and steps so far, so the caller neither retries nor repeats them. Once a message went out, loop requests carry `allowEmpty` (the gateway does not retry an empty final answer). An interrupted run counts as `interrupted`, not `fallback`, in the `ai_runs_total` metric (the row keeps `fallback` + guardrail `interrupted`). `send_message` failures (`nothing_to_send`, `not_delivered`) are `ok: false` steps. `retrieved[].used` = the sent text quotes the entry (whole answer or 6 consecutive words, accent-insensitive).
- Prompts: `sales-agent@13` (retail) and `@14` (hotel = @13 + the lodging section of @12), forced by `PROMPT_VERSION_OPTION` (13 | 14); fanpage comment replies add `fanpage-context@2`. Older versions stay in `packages/ai-core/prompts` for history. Line breaks: a stand-alone literal `\n` in the model text becomes a line break (T-135, `domain/reply-text.ts`).
- Customer images: optional `images` on the request (Hermes provider only; others throw so the caller can retry text-only).
- Situations (`<shop_situations>`, `domain/situations.ts`: enabled scenarios only, grouped under General / After-an-order headers, incl. their "Khi" trigger) take priority over the generic handoff rule in the prompt. Business profile (T-138): the last user turn starts with `<business_profile>` (`domain/business-profile.ts`); `{{bot.style}}` comes from `domain/reply-style.ts`; the shop name is `profile.fields.displayName || placeholders['store.name'] || workspace.name`. The profile is data, never instructions.
- Focus products: up to 3 products from the last 3 runs of the conversation (`ai_runs.product_ids`; playground: last 30 minutes) in `<focus_products>`; a comment reply never reads or writes that memory. No URL is ever in the model context or taken from model output.
- Bot API actions (T-055, `application/action-tools.ts`, `docs/actions.md`): one write tool `action_<n>` per enabled action plus `confirm_pending_action` / `cancel_pending_action` while a confirmation waits (`<pending_action>` block). At most 3 executions per turn (a 4th gives the fallback with guardrail `action_loop_limit`); a confirm-required call is only stored and the read-back goes to the model; confirm runs the STORED arguments, never a call stored in the same turn; comment replies get `confirmation_not_available`. Idempotency key `act:<conversationId>:<actionId>:<args-hash>:<10-min bucket>`; the playground uses a stable per-bot UUID as conversation id.
- A provider that cannot be built (bad key, wrong `SECRETS_ENCRYPTION_KEY`) is skipped and logged; its routes run on their fallback.
- Every LLM turn writes one `ai_runs` row (playground: `is_test = true`).

**Do not:** call provider SDKs outside `packages/ai-core`; log prompts, replies or API keys; read `bots`/`knowledge_items` tables directly (use the facades).

**Prompt evals (T-145):** `evals/` + `modules/ai/evals/` + `src/cli/eval.ts` run YAML cases through `PlaygroundService` (scripted fake model with tool calls in `pnpm test`, real model with `--live`); see `apps/backend/evals/README.md`. Fake mode replays each case's `fake_turns` (scripted model responses: tool calls, then the free-text answer; a tool-less request is the history summarizer) and the checks read the delivered messages (joined text, pictures, message count). A prompt or model change needs the critical cases at 100% live.
