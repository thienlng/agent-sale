# @agent-sales/db

Drizzle schema, SQL migrations, tenant-scoped transactions and DB roles. **Only `infrastructure/` folders and test helpers may import this package** (enforced by `pnpm arch`).

## Rules (ADR-004, docs/05 §9)

- Every tenant table has `workspace_id`, forced RLS and the InitPlan predicate `workspace_id = (select nullif(current_setting('app.workspace_id', true), '')::uuid)`.
- Tenant access only through `withTenant(db, workspaceId, tx => …)` — transaction-scoped `set_config`, verified after set. Cross-tenant work through `withSystem` (role marker, audited), used only by: webhook ingress channel lookup and event insert, the Meta OAuth callback (state consume), the agent's inbox-queue claim/lease/complete/dead-letter, scheduler/outbox publisher, reconciliation, analytics rollups, the `account` module's global `accounts`/`account_members` tables the `account-backfill` and `bot-profile-backfill` (T-141) CLIs, back-office, and the business purge of the worker (`purgeWorkspaceRows`, ADR-032, ADR-004 amendment 2026-11-12) (ADR-004 amendments 2026-10-24 and 2026-10-28; T-048 narrows the first three).
- Business purge (ADR-032, `src/purge.ts`): `purgeWorkspaceRows(systemDb, ws)` deletes every row of one business from every table of schema `public` with a `workspace_id` column, read from the catalog at run time (children before parents from `pg_constraint`, 2 000 rows per transaction, resumable), except `PURGE_RETAINED_TABLES` (`audit_events`, `message_usage`, `workspaces`). A new tenant table is purged automatically; one that must survive a purge goes into that list with a reason. Its migration must grant `app_system` `DELETE` (`purge.integration.test.ts` fails otherwise).
- Account-scoped tables (owner assistant, ADR-024): `assistant_threads`, `assistant_messages`, `assistant_runs`, `assistant_run_steps`, `assistant_memory`, `assistant_proposals` carry `account_id`, forced RLS, and the predicate `account_id = (select nullif(current_setting('app.account_id', true), '')::uuid)` (`accountPolicies` in `schema/workspace.ts`). Access only through `withAccount(db, accountId, tx => …)` on the tenant login — same contract as `withTenant` (transaction-scoped `set_config`, verified after set). `assistant_messages.search` is a generated column absent from the Drizzle table; query it with `sql` (ADR-004 amendment 2026-11-02).
- Global tables (no `workspace_id`): `users`, `tenant_routes`, `outbox_events` (nullable), `inbox_events` — plus the list in docs/05 §9 as modules are added.
- Schema lives in `src/schema/<module>.ts` (one file per backend module). Migrations are SQL in `migrations/`; `drizzle-kit generate` helps draft them, roles/policies/partitions are hand-written. `drizzle-kit push` is banned.
- Owner assistant SQL lane (T-171, migration 0060): schema `assistant_sql` holds 11 read-only `security_barrier` views (`businesses`, `orders`, `order_items`, `products`, `product_variants`, `customers`, `conversations`, `channels`, `bots`, `activity_events`, `lodging_bookings`) owned by the NOLOGIN `app_assistant_reader`. The reader has column-level `SELECT` on exactly the base columns the views read (never phone, email, address, birthday, gender, notes, message data, tokens, settings or external ids) and one `FOR SELECT` policy per base table: the rows of the businesses in `app.assistant_business_ids` that also belong to the account in `app.account_id` (not deleted). `app_assistant_sql` (NOLOGIN group) has `USAGE` on the schema and `SELECT` on the views, nothing else. Query it only through `runAssistantSql(createAssistantSqlClient(url).sql, { accountId, businessIds, sql })` (`src/assistant-sql.ts`): one statement per `READ ONLY` transaction, both GUCs set transaction-locally and verified, 3 s statement timeout, `Asia/Ho_Chi_Minh`, at most `maxRows + 1` rows through a cursor. A migration that changes a column a view reads must recreate that view in the same migration. A non-superuser migrator needs `GRANT app_assistant_reader TO <migrator>` before 0060.
- Logins: `owner` runs migrations only; `rapiz_tenant` (∈ `app_tenant`) and `rapiz_system` (∈ `app_system`) are what apps use. `rapiz_assistant` (∈ `app_assistant_sql` only, optional, `DATABASE_ASSISTANT_SQL_URL`) is used by the `api` process for the owner assistant's SQL lane only; `ensureLoginRoles` creates it with `CONNECTION LIMIT 10` and the role defaults `default_transaction_read_only = on`, `statement_timeout = 3s`, `search_path = assistant_sql`, `idle_in_transaction_session_timeout = 5s`, `temp_file_limit = 256MB`, `work_mem = 16MB`, `track_activities = off` (needs a superuser migrator), repairs an existing login's group membership, and refuses a name shared with the tenant or system login. `migrate --dev-roles` / `--login-roles` create it only when `DATABASE_ASSISTANT_SQL_URL` is set. **Never connect an app as a superuser** — superusers bypass RLS even when it is forced. Every table with `workspace_id` (except global `tenant_routes`, `outbox_events`) must have RLS enabled + forced; an integration test enforces this.
- Connection: PgBouncer transaction mode → `prepare: false`, no session state, no `LISTEN`.

## Commands

```bash
pnpm --filter @agent-sales/db db:generate   # draft a migration from schema changes (review the SQL!)
pnpm --filter @agent-sales/db db:migrate    # apply migrations (DATABASE_URL)
pnpm --filter @agent-sales/db test
```

Local Postgres (pgvector image) comes with `infra/docker/docker-compose.local.yml` (T-004).
